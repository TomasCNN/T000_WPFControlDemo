# 999999009-30_NLog 异步写入是否生效的 6 种验证方法

验证的核心逻辑是：**同步写日志会在业务线程当场执行磁盘 IO，耗时毫秒级；异步写日志仅在业务线程做内存入队，耗时微秒级，且由独立后台线程批量落盘**。下面从「最简单直观」到「原理级确认」逐一说明，可根据场景选用。

------

## 方法一：耗时对比法（最直观，工业现场首选）

### 原理

同步写入：单条日志包含打开文件、写磁盘、关闭文件，耗时通常 **3~20ms**（受磁盘性能影响波动极大）；

异步写入：业务线程仅执行内存入队，耗时 **<0.1ms**（微秒级），两者相差几十到上百倍。

### 操作步骤

在日志调用前后加 `Stopwatch` 计时，打印耗时：

csharp：

```c#
var sw = Stopwatch.StartNew();
LogHelper.Info("测试模块", "验证异步写入耗时");
sw.Stop();

// 输出耗时，建议用Ticks更精准
Console.WriteLine($"单条日志调用耗时：{sw.ElapsedMilliseconds}ms / {sw.ElapsedTicks} 刻");
```

### 判断标准

- ✅ 异步生效：`ElapsedMilliseconds` 显示 0ms，Ticks 在几千到几万刻之间（对应几十微秒）；
- ❌ 同步模式：单条耗时 1ms 以上，且波动明显。

> 工业场景适配：可以直接在相机回调里埋点统计，对比「打日志前后的 CT 差值」，如果差值 <0.1ms，说明异步确实没有阻塞采集线程。

------

## 方法二：写入延迟验证法（利用批量写入特征）

### 原理

异步模式下，后台线程会攒够 `batchSize` 条、或者等待短暂间隔后才批量落盘，日志不会立刻出现在文件里；同步模式是写完一条立刻落盘。

### 操作步骤

1. 写一个循环，连续打 10 条日志；
2. 打完立刻打开日志文件查看内容。

csharp:

```c#
for (int i = 0; i < 10; i++)
{
    LogHelper.Info("测试", $"第{i}条测试日志");
}
// 立刻打开日志文件观察
```

### 判断标准

- ✅ 异步生效：打完立刻看文件，可能是空的 / 只有前几条，等待 1~ 几秒后才全部出现；
- ❌ 同步模式：打完立刻看，10 条日志全部完整写入文件。

> 注意：如果 `batchSize` 设得很小（比如 1），延迟会不明显；可以临时把 batchSize 改大再测，测完改回原值即可。

------

## 方法三：压测无阻塞验证（体感最明显）

### 原理

同步模式下，连续打大量日志会卡住主线程 / 业务线程；异步模式下，只是快速往内存队列里塞数据，主线程瞬间执行完，完全不卡。

### 操作步骤

在 UI 线程 / 业务线程里循环打 10000 条日志，观察界面会不会卡死、线程会不会阻塞：

csharp:

```c#
var sw = Stopwatch.StartNew();
for (int i = 0; i < 10000; i++)
{
    LogHelper.Debug("压测", $"压测日志第{i}条");
}
sw.Stop();
Console.WriteLine($"1万条日志入队总耗时：{sw.ElapsedMilliseconds}ms");
```

### 判断标准

- ✅ 异步生效：1 万条日志入队耗时 <50ms，界面完全不卡顿，瞬间执行完成；后续磁盘慢慢写；
- ❌ 同步模式：执行时间几百毫秒到几秒不等，界面明显卡顿假死。

------

## 方法四：NLog 内部日志验证（最权威，配置级确认）

### 原理

NLog 自身有内部日志，可以打印框架初始化过程。如果异步配置生效，内部日志会明确打印 `AsyncWrapper` 初始化、后台消费线程启动的记录。

### 操作步骤

1. 在 `NLog.config` 根节点开启内部日志：

xaml:

```xaml
<nlog internalLogLevel="Debug" 
      internalLogFile="D:/Logs/nlog-internal.log">
```

1. 运行程序一次，然后打开 `nlog-internal.log` 文件。

### 判断标准

搜索关键词 `AsyncWrapper`、`AsyncTargetWrapper`、`Starting asynchronous writer`：

- ✅ 异步生效：能找到类似日志，说明异步包装器已成功加载并启动后台线程；

plaintext:

```tex
Info: Adding target AsyncWrapper_MainLog(AsyncWrapper)
Info: Starting asynchronous writer for target MainLog
```

- ❌ 未生效：找不到任何 AsyncWrapper 相关记录，说明配置没生效，退化为同步模式。

> 这是排查「配置写了但没生效」的终极方法，能直接看到 NLog 有没有识别到异步配置。

------

## 方法五：线程调试法（原理级验证，确认后台消费线程）

### 原理

异步模式会为每个独立的 `AsyncWrapper` 启动一条**后台低优先级消费线程**；同步模式不会额外创建写日志线程。

### 操作步骤（VS 调试）

1. 在日志调用处打一个断点；
2. 命中断点后，打开「调试 → 窗口 → 线程」；
3. 观察线程列表，查找名称包含 `Async`、`NLog`、`Writer` 的后台线程。

### 判断标准

- ✅ 异步生效：能看到 1 条或多条 NLog 异步写盘专用的后台线程，线程优先级为「低于正常」；
- ❌ 同步模式：没有专属的日志写盘线程，日志写入直接发生在业务线程。

> 补充：也可以用「性能探测器」观察线程数，程序启动后线程数比同步模式多 1~N 个（对应 N 个异步 Target）。

------

## 方法六：溢出策略验证法（机制级确认）

### 原理

只有异步模式才有队列容量和溢出策略。如果 `overflowAction="Discard"` 真的生效，队列满时会直接丢弃新日志，不会阻塞业务线程；如果是 `Block` 则会卡住业务线程。

### 操作步骤

1. 临时把队列容量改到极小，溢出策略设为 `Discard`：

xaml:

```xaml
<targets async="true" queueLimit="10" overflowAction="Discard">
```

1. 业务线程循环打 10000 条日志，观察线程是否卡住。

### 判断标准

- ✅ 异步生效：循环瞬间执行完成，完全不卡顿，最终日志文件里只有前十几条 + 后续批量写入的部分，中间大量被丢弃；
- ❌ 同步模式 / 配置未生效：没有队列概念，要么全部写完（慢），要么直接卡住。

> 工业场景建议额外验证：把 `overflowAction` 临时改成 `Block`，业务线程会明显卡住，说明队列机制确实在工作；测完务必改回 `Discard`。

------

## 工业场景推荐验证组合

1. **快速验证**：用方法一（耗时法），10 秒就能确认业务线程是否被阻塞；
2. **配置排查**：用方法四（内部日志），确认 NLog 确实加载了异步配置；
3. **上线前确认**：方法一 + 方法三（压测），确认高并发下也不会卡业务线程。

## 常见「配置写了但异步没生效」的原因排查

1. **配置文件没复制到输出目录**

   最常见：`NLog.config` 的「复制到输出目录」没设为「如果较新则复制」，程序读到的是旧配置甚至没读到配置，默认同步。

2. **`async="true"` 放错了节点**

   必须写在 `<targets>` 根节点上，写在 `<target>` 单个节点上不生效。

   ✅ 正确：`<targets async="true">`

   ❌ 错误：`<target xsi:type="File" async="true">`

3. **配置语法错误，NLog fallback 到默认同步**

   配置写错（比如节点拼写错误、属性名错），NLog 会忽略错误部分，退化为默认同步行为；看内部日志能直接看到报错。

4. **使用了不支持异步包装的特殊 Target**

   极少数第三方 Target 不兼容 AsyncWrapper，但内置的 File、Console 等全部支持。

5. **调用了 `LogManager.Flush()` 后立刻判断**

   Flush 会强制等待队列全部落盘，会掩盖异步的延迟特征，不要在压测 / 耗时验证前调用。
