# 003011016_三个 WPF 分层架构核心问题

## 问题一：项目结构中分层架构是如何组织文件夹的？

### 核心原则：**按职责分层，而非按功能模块；依赖方向严格从上到下，下层绝对不依赖上层**

工业上位机的文件夹组织必须**一眼就能看出架构和依赖关系**，让任何一个开发者打开项目就能快速找到对应的代码。

### 一、标准分层文件夹结构（带数字前缀）

plaintext

```tex
IndustrialVisionTemplate/
├── 01_Abstractions/          # 第1层：硬件抽象层（最底层，所有上层都依赖它）
├── 02_Implementations/        # 第2层：硬件具体实现（依赖抽象层）
├── 03_Services/               # 第3层：服务层（依赖抽象层和实现层）
├── 04_Business/               # 第4层：业务逻辑层（依赖服务层）
├── 05_ViewModels/             # 第5层：MVVM层（依赖业务层和服务层）
├── 06_Views/                  # 第6层：UI层（依赖ViewModel层）
├── 07_Models/                 # 公共数据模型层（所有层都可以依赖）
├── 08_Data/                   # 数据访问层（依赖模型层）
├── 09_Common/                 # 通用工具层（所有层都可以依赖）
└── Configs/                   # 配置文件
```

**为什么用数字前缀？**

- 解决方案管理器会**按数字顺序自动排列**，正好对应依赖方向（01→09）
- 一眼就能看出哪个是底层、哪个是上层
- 避免开发者把上层代码放到下层文件夹中

### 二、每个文件夹的详细职责与内容规范

| 文件夹                 | 层级       | 核心职责                               | 包含文件类型             | 命名规范                          | 禁止放入                   |
| :--------------------- | :--------- | :------------------------------------- | :----------------------- | :-------------------------------- | :------------------------- |
| **01_Abstractions**    | 硬件抽象层 | 定义所有硬件和服务的统一接口，隔离变化 | 接口文件 (.cs)           | `Ixxx.cs`                         | 任何实现类、任何业务逻辑   |
| **02_Implementations** | 硬件实现层 | 不同品牌硬件的具体实现                 | 实现类 (.cs)             | `XxxYyy.cs`（如 IkCamera.cs）     | 任何业务逻辑、任何 UI 代码 |
| **03_Services**        | 服务层     | 封装通用能力，提供强类型方法           | 服务类 (.cs)             | `XxxService.cs`                   | 任何 UI 代码、任何业务流程 |
| **04_Business**        | 业务逻辑层 | 核心业务流程编排、业务规则             | 流程类、状态机类         | `XxxProcess.cs`、`XxxManager.cs`  | 任何硬件操作、任何 UI 代码 |
| **05_ViewModels**      | MVVM 层    | UI 逻辑、数据绑定、命令                | ViewModel 类             | `XxxViewModel.cs`                 | 任何硬件操作、任何业务逻辑 |
| **06_Views**           | UI 层      | 界面布局、样式、控件                   | XAML 文件                | `XxxView.xaml`                    | 任何业务逻辑、任何硬件调用 |
| **07_Models**          | 数据模型层 | 纯数据结构，无任何逻辑                 | 实体类、DTO 类           | `Xxx.cs`（如 Defect.cs）          | 任何方法、任何逻辑         |
| **08_Data**            | 数据访问层 | 数据库、文件读写                       | 数据库上下文、文件管理器 | `XxxContext.cs`、`XxxManager.cs`  | 任何业务逻辑               |
| **09_Common**          | 通用工具层 | 所有模块通用的辅助类                   | 转换器、扩展方法、帮助类 | `XxxConverter.cs`、`XxxHelper.cs` | 任何业务相关代码           |

### 三、子文件夹组织规范

每个主文件夹下可以按功能模块再拆分子文件夹，**保持同一层级的职责单一**：

plaintext

```tex
02_Implementations/
├── Cameras/                  # 所有相机实现
│   ├── IkCamera.cs
│   ├── HikCamera.cs
│   └── BaslerCamera.cs
├── Plcs/                     # 所有PLC实现
│   ├── SiemensPlc.cs
│   ├── OmronPlc.cs
│   └── MitsubishiPlc.cs
└── Loggers/                  # 所有日志实现
    └── NLogLogger.cs

06_Views/
├── MonitorView/              # 实时监控模块
│   ├── MonitorView.xaml
│   └── MonitorView.xaml.cs
├── ParameterView/            # 参数配置模块
│   ├── ParameterView.xaml
│   └── ParameterView.xaml.cs
└── DataView/                 # 数据记录模块
    ├── DataView.xaml
    └── DataView.xaml.cs
```

### 四、绝对禁止的错误组织方式

❌ **按功能模块分层**：把相机、PLC、算法各自做成一个大模块，每个模块包含所有层的代码

❌ **混合职责**：把硬件实现和业务逻辑放在同一个文件夹

❌ **反向依赖**：抽象层依赖实现层，业务层依赖 ViewModel 层

❌ **无组织乱放**：所有.cs 文件都放在根目录下

## 问题二：如何完善硬件抽象层、服务层和业务逻辑层？

这三层是工业上位机的**核心骨架**，完善程度直接决定了项目的可维护性、可扩展性和稳定性。

### 一、完善硬件抽象层（HAL）：工业软件的灵魂

**核心目标**：**让上层代码完全不关心具体用的是什么硬件**，换硬件只需要改一行配置。

#### 1. 接口设计三大原则

- **最小接口原则**：每个接口只包含最核心的方法，不要做 "胖接口"
- **面向行为原则**：接口定义 "能做什么"，而不是 "是什么"
- **异常统一原则**：所有实现抛出统一的异常类型

#### 2. 常见问题与完善方法

| 常见问题                         | 完善方案                        | 代码示例 |
| :------------------------------- | :------------------------------ | :------- |
| 接口太胖，包含很多特定硬件的方法 | 拆分接口，使用接口继承          |          |
| 接口没有继承IDisposable          | 所有硬件接口必须继承IDisposable |          |
| 没有统一的异常类型               | 定义硬件专属异常                |          |
|                                  |                                 |          |

{
    public string HardwareType { get; }
    public string ErrorCode { get; }

#### 3. 终极完善：添加工厂模式

通过工厂模式根据配置动态创建硬件实例，彻底实现硬件可插拔：
```csharp
public class HardwareFactory
{
    private readonly ILogger _logger;
    private readonly ConfigService _configService;

    public HardwareFactory(ILogger logger, ConfigService configService)
    {
        _logger = logger;
        _configService = configService;
    }

    public ICamera CreateCamera()
    {
        var config = _configService.CurrentConfig.Camera;
        return config.Type switch
        {
            "Ik" => new IkCamera(_logger, config),
            "Hik" => new HikCamera(_logger, config),
            "Basler" => new BaslerCamera(_logger, config),
            _ => throw new HardwareException($"不支持的相机类型：{config.Type}", "Camera", "UNSUPPORTED_TYPE", null)
        };
    }

    public IPlc CreatePlc()
    {
        var config = _configService.CurrentConfig.Plc;
        return config.Type switch
        {
            "Siemens" => new SiemensPlc(_logger, config),
            "Omron" => new OmronPlc(_logger, config),
            _ => throw new HardwareException($"不支持的PLC类型：{config.Type}", "PLC", "UNSUPPORTED_TYPE", null)
        };
    }
}
```

### 二、完善服务层：通用能力的封装者

**核心目标**：**隐藏底层细节，为上层提供简单、安全、强类型的 API**。

#### 1. 服务层的三大职责

- 封装底层硬件的复杂操作
- 处理通用异常和重试逻辑
- 提供业务友好的强类型方法

#### 2. 常见问题与完善方法

| 常见问题                           | 完善方案                       | 代码示例 |
| :--------------------------------- | :----------------------------- | :------- |
| 直接暴露硬件地址，魔法字符串满天飞 | 封装成强类型方法，隐藏地址细节 |          |
| 上层代码直接写地址                 | 服务层封装                     |          |
| 没有异常处理，硬件异常直接抛到UI   | 服务层捕获并包装异常，添加日志 |          |
| 没有批量操作，频繁读写PLC导致卡顿  | 添加批量读写方法               |          |
|                                    |                                |          |

#### 3. 服务层最佳实践

- 所有服务都应该是**无状态**的
- 服务之间可以相互依赖，但不要形成循环依赖
- 耗时操作必须提供异步版本
- 所有硬件操作都必须加超时

### 三、完善业务逻辑层：核心流程的编排者
**核心目标**：**只做流程编排，不做任何具体实现**，所有具体操作都委托给服务层。

#### 1. 业务逻辑层的三大职责
- 核心业务流程的顺序控制
- 业务规则的判断和执行
- 设备状态的管理和转换

#### 2. 常见问题与完善方法
| 常见问题                             | 完善方案                       | 代码示例 |
| ------------------------------------ | ------------------------------ | -------- |
| 业务流程写在ViewModel中              | 把所有业务流程抽离到Business层 |          |
| ViewModel中写业务流程                | Business层封装流程             |          |
| 流程没有状态管理，容易出现并发问题   | 使用状态机管理设备状态         |          |
| 流程没有事务机制，异常时设备状态混乱 | 添加事务和补偿逻辑             |          |

//正确：使用状态机管理设备状态 
``` c#
public enum DeviceState
{
    Idle,
    Running,
    Paused,
    Error
}

public class StateMachine
{
    private DeviceState _currentState = DeviceState.Idle;

    public bool CanStart() => _currentState == DeviceState.Idle;

    public void Start()
    {
        if (!CanStart())
            throw new InvalidOperationException($"当前状态{_currentState}无法启动");
        
        _currentState = DeviceState.Running;
    }

    public void Stop()
    {
        _currentState = DeviceState.Idle;
    }

    public void SetError()
    {
        _currentState = DeviceState.Error;
    }
}
```

//正确：添加事务和补偿逻辑

public async Task<bool> RunAsync()
{
    try
    {
        await _plcService.SendStartSignal();
        var image = await _cameraService.GetBitmapAsync();
        var result = await _algorithmService.DetectDefectsAsync(image);
        await _plcService.SendEndSignal(result);
        return result;
    }
    catch (Exception ex)
    {
        // 异常时复位设备
        await _plcService.ResetAllSignals();
        _stateMachine.SetError();
        throw;
    }
}

## 问题三：如何在示例代码中融入异常处理等最佳实践？

工业软件的异常处理**不是简单的try-catch**，而是一套完整的**错误防御、恢复和上报机制**，必须贯穿所有层级。

### 一、异常处理分层原则

**底层抛出具体异常，中层包装通用异常，上层处理用户可见异常**

| 层级        | 异常处理方式                                     | 示例 |
| ----------- | ------------------------------------------------ | ---- |
| 硬件抽象层  | 捕获SDK异常，包装成统一的`HardwareException`抛出 |      |
| 服务层      | 捕获硬件异常，包装成`ServiceException`，添加日志 |      |
| 业务逻辑层  | 捕获服务异常，执行补偿逻辑，复位设备状态         |      |
| ViewModel层 | 捕获所有异常，显示用户友好的提示                 |      |
// 硬件抽象层  捕获SDK异常，包装成统一的`HardwareException`抛出

```c#
public Bitmap GetBitmap(int timeoutMs)

    	// SDK调用
    	return IK_SDK_GetImage();
	}
	catch (IkSdkException ex)
	{
    	throw new HardwareException("相机取图失败", "Camera", ex.ErrorCode.ToString(), ex);
	}
}
```
//服务层   捕获硬件异常，包装成`ServiceException`，添加日志

//业务逻辑层   捕获服务异常，执行补偿逻辑，复位设备状态

### 二、必须融入的工业级最佳实践

#### 1. 资源自动释放（IDisposable模式）

所有硬件和非托管资源必须实现完整的IDisposable模式：
```csharp
public class IkCamera : ICamera
{
    private bool _disposed = false;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 释放托管资源
            StopCapture();
        }

        // 释放非托管资源
        IK_SDK_CloseDevice();
        _lineScanImage?.Dispose();
        _lineScanImage = null;

        _disposed = true;
    }

    ~IkCamera()
    {
        Dispose(false);
    }
}
```

#### 2. 超时和重试机制

所有硬件操作必须加超时，关键操作添加重试：

csharp:

```c#
public bool WriteShort(string address, short value, int retryCount = 3)
{
    for (int i = 0; i < retryCount; i++)
    {
        try
        {
            return _plc.WriteShort(address, value);
        }
        catch (Exception ex)
        {
            _logger.Warn($"PLC写入失败，第{i+1}次重试：{ex.Message}");
            Thread.Sleep(10);
        }
    }

    throw new HardwareException($"PLC写入失败，已重试{retryCount}次", "PLC", "WRITE_FAILED", null);
}
```

#### 3. 安全复位机制

任何异常发生时，必须复位所有硬件信号，防止设备卡死：

csharp:

```c#
public async Task ResetAllSignals()
{
    try
    {
        await WriteBoolAsync(_config.StartTriggerAddress, false);
        await WriteBoolAsync(_config.EndTriggerAddress, false);
        await WriteBoolAsync(_config.AlarmAddress, false);
        _logger.Info("所有PLC信号已复位");
    }
    catch (Exception ex)
    {
        _logger.Error("PLC信号复位失败", ex);
    }
}
```

#### 4. 完整的日志记录

每个层级都要记录日志，不同级别日志包含不同信息：

csharp:

```c#
// Debug级别：调试信息
_logger.Debug($"相机取图耗时：{sw.ElapsedMilliseconds}ms");

// Info级别：正常流程
_logger.Info("检测流程完成，结果：OK");

// Warn级别：警告信息
_logger.Warn($"PLC写入重试，地址：{address}");

// Error级别：异常信息
_logger.Error($"相机初始化失败：{ex.Message}", ex);
```

#### 5. 防御性编程

所有公共方法都要做参数校验：

csharp:

```c#
public Bitmap GetBitmap(int timeoutMs = 3000)
{
    if (timeoutMs <= 0)
        throw new ArgumentOutOfRangeException(nameof(timeoutMs), "超时时间必须大于0");

    if (_disposed)
        throw new ObjectDisposedException(nameof(IkCamera));

    // 业务逻辑
}
```

## 总结

1. **文件夹组织**：按职责分层，用数字前缀保证顺序，每个文件夹职责单一

2. **三层完善**：

   - 硬件抽象层：定义统一接口，用工厂模式实现硬件可插拔
   - 服务层：封装底层细节，提供强类型 API
   - 业务逻辑层：只做流程编排，用状态机管理设备状态

   

3. **异常处理**：遵循 "底层抛出，中层包装，上层处理" 的原则，配合资源释放、超时重试、安全复位
