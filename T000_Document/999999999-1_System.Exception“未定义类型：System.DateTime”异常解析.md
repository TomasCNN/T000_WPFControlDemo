

# 999999999-1_System.Exception:“未定义类型：System.DateTime”异常解析

这个异常**不是.NET 框架自带的标准系统异常**（标准类型加载错误会抛出 `TypeLoadException` / `ArgumentException`），它几乎都是**自定义的类型解析器、数据映射组件、序列化工具、协议通信库**抛出的，核心含义是：**当前组件的类型白名单 / 映射表中，没有注册 `System.DateTime` 类型，无法识别和处理该类型**。

结合工业软件开发的常见场景，按出现概率从高到低，对应原因和解决方案如下：

------

## 一、最高概率：自定义类型映射 / 解析工具遗漏了 DateTime

### 场景说明

工业项目中经常会写通用的类型转换工具、数据点映射器、配置解析器，根据字符串类型名（如 `"System.Int32"`、`"System.Double"`）来匹配 C# 类型，实现数据自动转换。

这类工具通常只覆盖了 int、double、bool、string 等基础数值类型，**漏掉了 DateTime 结构类型**，当配置的点位 / 字段类型为日期时间时，就会抛出 “未定义类型”。

这也是工业数据采集、配置化开发中最常见的踩坑点。

### 排查点

- 异常堆栈指向自己写的 `TypeConverter`、`DataTypeParser`、`DataPointMapper` 等工具类
- 报错发生在加载点位配置、解析数据类型、批量转换数据时

### 解决方案

在你的类型映射字典中，补充 `DateTime` 的映射关系。

#### 反例（遗漏 DateTime）

csharp：

```c#
// 常见的类型映射表，只写了基础类型，漏掉了DateTime
private static readonly Dictionary<string, Type> TypeMap = new()
{
    ["System.Int32"] = typeof(int),
    ["System.Double"] = typeof(double),
    ["System.Boolean"] = typeof(bool),
    ["System.String"] = typeof(string)
};

// 解析类型时找不到就抛异常
public static Type ParseType(string typeName)
{
    if (TypeMap.TryGetValue(typeName, out var type))
        return type;
    throw new Exception($"未定义类型：{typeName}"); // 就是你遇到的异常
}
```

#### 修正后

csharp:

```c#
private static readonly Dictionary<string, Type> TypeMap = new()
{
    ["System.Int32"] = typeof(int),
    ["System.Double"] = typeof(double),
    ["System.Boolean"] = typeof(bool),
    ["System.String"] = typeof(string),
    // 补充 DateTime 类型映射
    ["System.DateTime"] = typeof(DateTime),
    ["DateTime"] = typeof(DateTime), // 兼容简写
    // 建议同步补充 TimeSpan 等常用结构
    ["System.TimeSpan"] = typeof(TimeSpan)
};
```

## 二、高频场景：序列化 / 反序列化组件的类型限制

### 场景说明

1. 自己封装的 JSON/XML 序列化工具，做了类型白名单校验，只允许基础类型通过，DateTime 不在白名单内
2. 使用了小众、老旧的序列化库，原生不支持 DateTime 类型
3. 动态构建数据契约时，只注册了数值、字符串类型，遗漏了日期时间类型

### 排查点

- 异常发生在对象序列化、JSON 解析、数据契约构建时
- 堆栈指向序列化相关的方法

### 解决方案

1. **优先使用官方成熟序列化库**：`System.Text.Json` 或 `Newtonsoft.Json`，二者原生完整支持 DateTime 类型，无需额外配置
2. 如果必须使用自定义序列化器，在类型白名单中添加 `DateTime`，并实现对应的序列化 / 反序列化逻辑

#### 工业场景最佳实践

跨系统 / 跨设备通信时，**不要直接传输 DateTime 对象**，推荐转成 **Unix 时间戳（long 类型）** 或 **固定格式字符串（yyyy-MM-dd HH:mm:ss）**，兼容性最强，完全避免类型不兼容问题。

csharp:

```c#
// 发送方：DateTime 转时间戳
long timestamp = new DateTimeOffset(dateTime).ToUnixTimeSeconds();

// 接收方：时间戳转回 DateTime
DateTime dateTime = DateTimeOffset.FromUnixTimeSeconds(timestamp).LocalDateTime;
```

## 三、常见场景：数据访问层 / ORM 的类型映射缺失

### 场景说明

- 自己实现的轻量级数据库访问层、DataTable 构建工具，只处理了数值、字符串类型，没处理 DateTime 到数据库日期类型的映射
- 使用小众 ORM 组件，不支持 DateTime 类型的自动映射
- 动态构建 DataTable 列时，类型列表里没加 DateTime

### 排查点

- 执行数据库查询、写入，或者构建 DataTable 时报错
- 堆栈指向数据访问层、DataTable 构建代码

### 解决方案

1. 在数据类型映射中补充 DateTime 与数据库日期类型（`datetime`、`datetime2`）的对应关系
2. 动态构建 DataTable 时，允许使用 DateTime 作为列类型

csharp:

```c#
// 动态构建DataTable列，补充DateTime支持
dataTable.Columns.Add("CreateTime", typeof(DateTime));
```

## 四、工业特有场景：协议通信 / 表达式解析器不支持 DateTime

### 场景说明

1. **设备通信 / PLC 交互**：很多工业协议（如部分自定义协议、老款设备驱动）只支持 int、float、bool 等基础数据类型，不支持日期时间类型，传入 DateTime 参数就会报未定义类型
2. **公式 / 表达式解析器**：工业软件常用的配方计算、逻辑表达式引擎，内置类型没有注册 DateTime，表达式中用到日期运算就报错

### 排查点

- 调用设备读写、数据上传、公式计算时报错
- 异常来自通信组件、表达式引擎

### 解决方案

1. **设备通信**：把 DateTime 拆分成多个整数（年、月、日、时、分、秒），或者转成时间戳（long）再传输，设备侧再还原
2. **表达式解析器**：在引擎的类型白名单中注册 `System.DateTime`，并补充常用的日期运算方法

------

## 五、通用排查步骤

1. **查看完整异常堆栈**：定位抛出异常的具体类和方法，确定是哪个组件抛出的错误
2. **确认上下文**：报错时正在执行什么操作（类型解析？序列化？数据库写入？设备通信？）
3. **检查该组件的类型列表**：查看组件的支持类型、映射字典、白名单，确认是否遗漏了 DateTime

------

## 工业开发最佳实践总结

1. **跨系统传输优先用时间戳**：和 PLC、MES、第三方系统交互时，用 long 型 Unix 时间戳代替 DateTime，彻底避免类型不兼容问题
2. **通用工具类补全常用结构**：写类型映射、转换工具时，除了基础类型，一定要覆盖 DateTime、TimeSpan、Guid 等常用结构
3. **优先使用成熟组件**：序列化、ORM 优先用官方 / 主流库，不要轻易自己实现完整的序列化 / 类型系统，容易遗漏边界类型
