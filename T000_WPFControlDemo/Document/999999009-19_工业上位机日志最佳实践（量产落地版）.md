# 999999009-19_工业上位机日志最佳实践（量产落地版）

工业上位机日志的核心目标是**故障可追溯、生产可审计、性能可优化，且日志本身绝不能成为设备故障源**。结合工控 7×24 小时运行、实时性要求高、现场运维能力弱的特点，以下从架构、内容、性能、运维、合规、场景落地六个维度给出可直接落地的最佳实践。

------

## 一、架构设计最佳实践：从根源适配工业场景

### 1. 全局异步写入优先，实时线程零 IO 阻塞

这是工业上位机日志的第一原则，没有之一。

- **为什么**：相机采集回调、PLC 实时控制、运动控制线程属于高优先级实时线程，同步写文件会产生几毫秒到几十毫秒的随机 IO 阻塞，直接导致相机丢帧、控制超时、CT 抖动，之前优化的取图性能会被日志完全抵消。

- **怎么做**：

  - NLog 配置 `<targets async="true">` 开启全局异步，业务线程仅将消息推入内存队列，立刻返回；
  - 自研日志用 `BlockingCollection` + 后台低优先级线程做消费者，统一批量写盘；
  - 异步队列溢出策略设为「丢弃新日志」，绝对不能阻塞主业务线程。

- **NLog 配置示例**：

  xaml:

  ```xaml
  <targets async="true" queueLimit="5000" overflowAction="Discard">
  ```

### 2. 严格五级分级，生产 / 调试差异化管控

统一使用 `Debug/Info/Warn/Error/Fatal` 五级，不同级别边界清晰，生产环境默认关闭 Debug，兼顾排查能力与运行性能。

| 级别  | 使用场景                         | 生产环境                     |
| :---- | :------------------------------- | :--------------------------- |
| Debug | 逐帧细节、中间变量、调试排查用   | ❌ 默认关闭，排查问题临时开启 |
| Info  | 关键状态切换、流程节点、操作记录 | ✅ 开启                       |
| Warn  | 单次异常、阈值预警、重试成功     | ✅ 开启                       |
| Error | 模块功能失效、连续失败           | ✅ 强制开启                   |
| Fatal | 程序崩溃、紧急停机               | ✅ 强制开启                   |

### 3. 多目标分流输出，排查效率最大化

不要把所有日志挤在一个文件里，按用途拆分不同输出目标，现场排查不用在百万行日志里翻找。

- **主运行日志**：Info 以上全级别，记录整体运行轨迹；
- **错误专属日志**：仅 Error/Fatal，出问题第一时间打开这个文件；
- **操作审计日志**：仅记录参数修改、模式切换、人工操作，满足合规审计；
- **调试专项日志**：Debug 级，排查单个模块时临时开启。

### 4. 封装统一入口，与日志框架解耦

封装一层静态日志工具类（如`LogHelper`），业务代码只调用工具类，不直接引用 NLog。

- 好处：后续更换日志框架、新增日志目标、扩展字段，只需修改工具类，不用动业务代码；
- 强制要求：所有模块必须通过统一入口打日志，禁止业务代码直接实例化 Logger。

### 5. 支持模块级粒度控制

可单独针对某个模块开启 Debug，其他模块保持 Info，排查问题时不会被无关日志刷屏。

- 典型场景：PLC 通信异常，只开 PLC 模块的 Debug 日志，相机、算法模块不受影响。

## 二、内容规范最佳实践：让日志真正有用

### 1. 毫秒级时间戳打底，时序可精确还原

工业设备动作周期短、并发多，秒级时间戳无法区分先后顺序，毫秒是最低要求。

- 标准格式：`yyyy-MM-dd HH:mm:ss.fff`
- 反例：只记录到秒，两个事件先后顺序完全无法判断，时序类问题根本查不了。

### 2. 强制标注模块归属，快速定位问题域

每条日志必须带模块名（线扫相机、PLC 通信、检测算法、MES 交互等），不用通读全文就能知道问题出在哪个环节。

- 正例：`[线扫相机] 取图超时，超时阈值500ms`
- 反例：`取图超时了`（不知道哪个相机、哪个工位）

### 3. 业务上下文透传，支持全链路追溯

关键日志必须携带业务标识，出问题后可通过标识串联全流程日志，这是生产追溯的核心。

- 必带上下文：批次号、产品 SN、帧序号、工位号、任务 ID；
- 实现方式：用 NLog 的`ScopeContext`统一注入，不用每条日志手动拼接字符串。

### 4. 异常必带完整堆栈，拒绝只打错误消息

Error/Fatal 级日志必须传入完整`Exception`对象，不能只打`ex.Message`。

- 只打消息：`参数无效`，完全不知道哪行代码、什么原因；
- 打完整堆栈：直接定位到具体文件、具体行号，现场不用复现也能排查。
- 正例：`LogHelper.Error("PLC通信", "写入D200失败", ex);`
- 反例：`LogHelper.Error("PLC通信", "失败了：" + ex.Message);`

### 5. 量化描述，禁用模糊表述

所有预警、状态描述用数值说话，不用形容词。

- 正例：`图像队列当前长度22，超过警戒阈值10，存在丢帧风险`
- 反例：`队列有点长，可能要卡了`（无法判断严重程度）

### 6. 通信类日志闭环，请求响应成对

相机、PLC、MES 等交互类日志，必须记录「发了什么、回了什么、结果如何」，排查通信问题不用抓包。

- 必带字段：设备地址、寄存器 / 指令、发送值、返回值、错误码、重试次数；
- 正例：`PLC读取D100失败，从站地址1，错误码0x07，第2次重试`

### 7. 操作审计三要素：谁、改了什么、结果如何

所有人工参数修改、模式切换、复位操作，必须满足审计要求。

- 三要素：操作人、修改前值、修改后值；
- 正例：`操作员001 修改检测阈值，旧值0.85 → 新值0.90，修改成功`

## 三、性能与高可用最佳实践：7×24 小时稳定运行

### 1. 高频循环日志降级，杜绝刷屏式输出

高帧率相机回调、PLC 轮询循环、算法处理循环等高频执行路径，禁止打 Info 及以上日志。

- 原则：逐帧 / 逐次的细节只能打 Debug，生产环境默认关闭，零性能开销；
- 统计信息可降级为间隔输出，比如每 100 帧、每 1 分钟打一次统计日志，代替逐帧打印。

### 2. 异步队列限流，优先保障主程序稳定

异步内存队列必须设置上限，极端情况下（程序疯狂抛异常）队列满了直接丢弃新日志，绝不能让日志把内存撑爆、把程序拖垮。

- 工业铁律：设备正常生产 > 日志完整，永远不能本末倒置。

### 3. 自动滚动切割 + 过期清理，杜绝磁盘占满

工控机无人值守，日志无限增长最终会写满磁盘，导致程序崩溃、设备停机。

- 按天切割文件，单文件过大（如 100MB）也强制切割；
- 自动清理 30~90 天前的旧日志，可根据磁盘大小调整；
- 额外建议：监控磁盘使用率，达到 80% 时触发预警。

### 4. 保持文件句柄常开，减少 IO 开销

不要每次写日志都打开关闭文件，高频场景下开闭文件的开销不可忽视。

- NLog 配置：`keepFileOpen="true"`，长期持有文件句柄，大幅提升写入性能。

### 5. 减少托管内存分配，避免 GC 尖刺

实时线程内不要做复杂的字符串拼接、大量插值字符串，会产生临时对象触发 GC，造成 CT 抖动。

- 简单日志直接输出，复杂调试信息只在 Debug 级别启用；
- 避免在日志里做大量格式化运算，提前做好值的计算。

### 6. 日志自身故障静默降级

写日志失败（磁盘满、权限不足）不能抛出异常到业务层，不能因为日志崩了主程序。

- 内部捕获异常、静默处理，最多在日志框架自身日志里记录，不影响业务。

### 7. 崩溃兜底：异常退出强制刷盘

程序正常退出、异常崩溃时，必须强制把内存队列里的剩余日志刷到磁盘，保留最后一刻的故障现场。

- NLog：程序退出时调用 `LogManager.Shutdown();`
- 自研日志：实现`Flush()`方法，在全局异常处理里调用。

## 四、运维与排查最佳实践：现场问题快速定位

### 1. 日志存放非系统盘，故障后可追溯

绝对不要把日志存在 C 盘 / 系统盘。

- 原因：工控机系统崩溃、重装系统时，C 盘数据会全部丢失，故障原因再也查不到；
- 建议：存在 D 盘或独立数据分区，路径固定，如`D:\EquipmentLogs\产线1号工位\`。

### 2. 支持动态调整级别，无需重启设备

生产环境出问题时，不用重启程序就能临时开启 Debug 日志，排查完再改回去，不影响生产。

- NLog 实现：配置`autoReload="true"`，修改配置文件后自动生效，一般 10 秒内生效；
- 自研实现：用变量控制级别，支持配置文件热更新。

### 3. 关键节点全埋点，还原设备运行轨迹

在程序生命周期的关键节点必须打 Info 日志，拿到日志就能还原设备做了什么。

- 必埋点：程序启动 / 退出、相机打开 / 关闭、PLC 连接 / 断开、模式切换（手动 / 自动）、批次开始 / 结束、参数加载完成、算法初始化结果。

### 4. 性能埋点常态化，瓶颈可量化

关键耗时路径必须打耗时日志，持续监控性能变化，提前发现卡顿隐患。

- 你的场景必埋点：取图总耗时、图像拷贝耗时、算法检测耗时、PLC 通信耗时、MES 上报耗时；
- 价值：不用等现场卡到不行才排查，通过日志趋势提前发现性能退化。

## 五、安全与合规最佳实践：满足工业审计要求

### 1. 敏感信息强制脱敏

禁止明文记录密码、密钥、核心工艺参数、客户隐私信息。

- 禁止内容：数据库密码、PLC 密码、接口 Token、产品核心配方参数、身份证号、手机号。

### 2. 审计日志不可随意篡改

操作审计日志单独存放，设置文件只读权限，仅程序可追加，禁止修改、删除历史记录，满足医药、食品等行业的合规要求。

### 3. 禁止记录大容量二进制数据

绝对不能把图像像素数组、完整文件流、原始报文大数据塞进日志，会让日志文件体积指数级增长，瞬间写满磁盘。

- 图像类数据：只记录宽高、路径、结果，不存像素内容。

## 六、典型场景正确写法示例（贴合你的视觉上位机场景）

### 1. 相机采集回调（高频场景）

✅ 正确：仅错误必打，逐帧细节用 Debug

csharp:

```c#
private static void LineScanCCD_OnResultDataGrab(OpencvImage opencvImage)
{
    try
    {
        // ... 取图逻辑 ...
        LogHelper.Debug("线扫相机", $"新一帧完成，宽{opencvImage.Width} 高{opencvImage.Height}");
    }
    catch (Exception ex)
    {
        LogHelper.Error("线扫相机", "取图回调异常", ex);
    }
}
```

❌ 错误：每帧打 Info，生产环境刷屏

csharp:

```c#
LogHelper.Info("线扫相机", "又收到一帧图"); // 100fps每秒100条，完全无价值
```

### 2. PLC 读写通信

✅ 正确：失败带错误码、重试次数

csharp:

```c#
public bool WritePlc(string address, short value)
{
    try
    {
        bool result = _plcClient.Write(address, value);
        if (!result)
        {
            LogHelper.Warn("PLC通信", $"写入地址{address}失败，值{value}，返回失败");
            return false;
        }
        return true;
    }
    catch (Exception ex)
    {
        LogHelper.Error("PLC通信", $"写入地址{address}异常", ex);
        return false;
    }
}
```

### 3. 参数修改审计

✅ 正确：带操作人、旧值、新值

csharp:

```c#
public void UpdateDetectThreshold(double newValue)
{
    double oldValue = DetectThreshold;
    DetectThreshold = newValue;
    LogHelper.Info("参数管理", 
        $"操作员{CurrentOperator} 修改检测阈值：旧值{oldValue:F3} → 新值{newValue:F3}");
}
```

### 4. 异常捕获

✅ 正确：传完整 Exception 对象

csharp:

```c#
catch (Exception ex)
{
    LogHelper.Error("检测算法", "处理第1234帧异常", ex);
    return null;
}
```

❌ 错误：只打消息，无堆栈

csharp:

```c#
catch (Exception ex)
{
    LogHelper.Error("检测算法", "出错了：" + ex.Message);
}
```

## 七、绝对禁止的红线（碰了必出问题）

1. ❌ 禁止在实时线程（相机回调、运动控制）同步写日志；
2. ❌ 禁止 catch 静默吞异常，不打任何日志直接返回；
3. ❌ 禁止高频循环内打 Info 及以上日志刷屏；
4. ❌ 禁止异常只打 Message，不输出完整堆栈；
5. ❌ 禁止日志存系统盘，无自动清理机制；
6. ❌ 禁止日志队列无限增长，拖垮主程序；
7. ❌ 禁止明文记录密码、核心配方等敏感信息。

> 最后总结：工业上位机日志的精髓不是 “记得多”，而是 “关键时刻有用”—— 正常运行时安静无干扰，出问题时能靠日志快速定位、快速恢复生产。
