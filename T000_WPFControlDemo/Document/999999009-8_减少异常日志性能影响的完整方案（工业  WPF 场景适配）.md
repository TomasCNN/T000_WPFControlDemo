# 999999009-8_减少异常日志性能影响的完整方案（工业 / WPF 场景适配）

异常日志是所有日志类型中性能开销最高的一类：**异常抛出时的堆栈展开、对象创建本身就有数十倍于普通日志的 CPU 开销，再加上堆栈格式化、字符串拼接、磁盘写入，高频异常会迅速占满 CPU、触发频繁 GC，甚至拖垮整个主业务**。工业场景中设备断连、通信超时、数据校验失败等高频异常，是最常见的隐形性能杀手。

优化核心思路：**先从根源减少不必要的异常产生，再分级降低单条开销，最后对高频异常做聚合去重**，优先用最低成本获得最大收益。

------

## 一、根源治理：从源头减少不必要的异常抛出

异常本身的堆栈展开、对象创建开销远大于日志写入。90% 的异常性能问题，本质是「把预期内的业务失败当成异常来处理」，从设计层面消除这类无效异常，性价比最高。

### 1. 明确边界：业务预期失败不用异常

#### 核心原则

**异常只用于「非预期的系统错误」，预期内的业务失败走正常流程分支**。

- ✅ 该用异常：空引用、索引越界、文件损坏、驱动崩溃等代码 bug 或系统级故障；
- ❌ 不该用异常：PLC 通信超时、设备忙、参数超限、数据为空、校验失败等正常业务中必然会出现的失败。

#### 工业场景典型反例

- 每次 PLC 通信超时都抛异常 + 打完整堆栈，网络波动时每秒触发几十次；
- 用异常跳出循环、做条件判断，把异常当`goto`使用；
- 用户输入非法、设备未就绪，也抛异常记录堆栈。

### 2. 用「返回结果模式」替代异常抛出

对于预期内可能失败的操作，用返回值对象承载结果，从根源消除异常对象的创建、堆栈展开和异常日志开销。工业场景的设备通信、数据采集、参数校验等高频率操作，强烈推荐这种写法。

#### 方案 1：Try-Parse 模式（简单场景）

用`bool`返回值表示成功，`out`参数输出结果，完全不抛异常。

csharp:

```c#
// ✅ 工业通信常用写法：成功返回true，失败返回false，无异常开销
public bool TryReadTemperature(out double temperature)
{
    temperature = 0;
    try
    {
        if (!plc.IsConnected) return false;
        temperature = plc.ReadDouble("DB1.DBD0");
        return true;
    }
    catch
    {
        // 底层异常内部静默处理，不向上层抛出，避免每层都打日志
        return false;
    }
}

// 调用方：走正常分支，无异常、无堆栈、无额外GC
if (plc.TryReadTemperature(out var temp))
{
    temperatureText.Text = $"{temp:F1}℃";
}
else
{
    temperatureText.Text = "--";
    // 仅计数，不逐条打日志，累计失败再告警
    Interlocked.Increment(ref _readFailCount);
}
```

#### 方案 2：Result<T> 结果对象（复杂场景）

自定义通用结果类，包含成功状态、错误码、错误信息，适合需要返回失败详情的场景。

csharp:

```c#
public class Result<T>
{
    public bool IsSuccess { get; }
    public T Data { get; }
    public int ErrorCode { get; }
    public string ErrorMessage { get; }

    private Result(bool isSuccess, T data, int code, string msg)
    {
        IsSuccess = isSuccess;
        Data = data;
        ErrorCode = code;
        ErrorMessage = msg;
    }

    public static Result<T> Success(T data) => new(true, data, 0, string.Empty);
    public static Result<T> Fail(int code, string msg) => new(false, default, code, msg);
}

// 使用：业务失败直接返回，不抛异常
public Result<double> CalculateYield(string batchNo)
{
    if (string.IsNullOrWhiteSpace(batchNo))
        return Result<double>.Fail(1001, "批次号不能为空");
    
    var data = GetBatchData(batchNo);
    if (data == null)
        return Result<double>.Fail(1002, "批次不存在");
    
    return Result<double>.Success(data.GoodCount / data.TotalCount);
}
```

### 3. 瞬时异常先自动重试，失败再记录

工业通信、网络请求的瞬时抖动非常常见，单次失败完全可重试，没必要每次都打异常日志。

- 策略：内置重试机制（如重试 3 次，间隔递增），单次失败不记录，全部重试失败再打一条告警日志；
- 适用场景：PLC 通信、数据库访问、接口调用等瞬时故障高发的链路。

csharp:

```c#
// 带重试的通信方法，单次失败不打日志
public async Task<Result<bool>> WriteParameterAsync(int address, double value)
{
    int retryCount = 3;
    for (int i = 0; i < retryCount; i++)
    {
        try
        {
            plc.Write(address, value);
            return Result<bool>.Success(true);
        }
        catch (CommunicationException)
        {
            if (i == retryCount - 1)
            {
                // 只有最后一次重试失败才打日志
                Log.Warning("写入参数失败，地址:{Addr}，已重试{Count}次", address, retryCount);
                return Result<bool>.Fail(2001, "通信重试失败");
            }
            await Task.Delay(10 * (i + 1)); // 递增等待
        }
    }
    return Result<bool>.Fail(2001, "通信重试失败");
}
```

## 二、分级记录：非必要不输出完整堆栈

就算确实需要记录异常，也不是所有异常都要打完整堆栈。堆栈格式化的 CPU 开销是普通消息的几十倍，按需输出粒度能大幅降低单条异常的性能损耗。

### 1. 异常分级输出策略

按严重程度和类型，匹配不同的日志粒度：

| 异常类型            | 定义                     | 日志级别 | 输出内容                        | 工业示例                           |
| :------------------ | :----------------------- | :------- | :------------------------------ | :--------------------------------- |
| 致命异常（Fatal）   | 程序崩溃、核心功能不可用 | Fatal    | 完整堆栈 + 上下文 + 系统环境    | 进程崩溃、数据库连不上、配置损坏   |
| 系统异常（Error）   | 非预期代码错误           | Error    | 异常类型 + 消息 + 完整堆栈      | 空引用、类型转换失败、文件读写异常 |
| 业务异常（Warning） | 预期内的业务失败         | Warning  | 错误码 + 错误消息，**不打堆栈** | 设备忙、参数超限、权限不足         |
| 瞬时异常（Info）    | 可自动恢复的临时故障     | Info     | 仅计数或简要提示，不单独记录    | 单次通信超时、网络抖动             |

### 2. 业务异常禁止输出堆栈

自定义业务异常类，只承载错误码和消息，日志记录时只输出消息，永远不输出堆栈跟踪。

csharp:

```c#
// 自定义业务异常：仅用于业务流转，不携带堆栈开销
public class BusinessException : Exception
{
    public int ErrorCode { get; }
    public BusinessException(int code, string message) : base(message)
    {
        ErrorCode = code;
    }
}

// 记录时只打消息，不打堆栈
catch (BusinessException ex)
{
    // ❌ 错误：传异常对象，框架会自动格式化堆栈
    Log.Warning(ex, "操作失败");
    
    // ✅ 正确：只记录错误码和消息，无堆栈开销
    Log.Warning("操作失败，错误码:{Code}，消息:{Msg}", ex.ErrorCode, ex.Message);
}
```

### 3. 利用异常过滤器只记录需要的异常

使用 C# 的`when`异常过滤器，只对系统级异常做完整记录，业务异常直接跳过日志输出。

csharp:

```c#
try
{
    ProcessProductionData(batch);
}
catch (Exception ex) when (ex is not BusinessException)
{
    // 只有非业务异常才打完整堆栈
    Log.Error(ex, "处理批次数据失败，批次号:{BatchNo}", batch.BatchNo);
    throw;
}
catch (BusinessException ex)
{
    // 业务异常只记消息，不打堆栈
    Log.Warning("批次处理业务失败：{Msg}", ex.Message);
}
```

## 三、聚合去重：解决高频重复异常的性能爆炸

工业场景最常见的性能坑：设备断连、通信超时类异常每秒触发几十上百次，每条都打堆栈，瞬间刷爆日志文件，同时占满 CPU。核心解法是**时间窗口聚合 + 状态变更触发**。

### 1. 滑动窗口聚合：同类型异常 N 秒只记 1 次

同一类异常在固定时间窗口内只输出第一条完整日志，后续只计数不输出；窗口结束时输出一条汇总，包含发生次数。

- 典型场景：通信断连、持续超限、传感器故障等持续性异常。
- 效果：日志量从每秒 N 条降到每分钟 1 条，CPU 开销下降 90% 以上。

### 2. 状态变更触发：发生 / 恢复各记一次

对于持续性故障，只在「故障首次发生」和「故障恢复」两个时间点各打一条日志，中间稳态不输出任何日志。

- 比如设备断连：断连瞬间打 1 条告警，重连成功打 1 条恢复，中间重连失败只计数、不打日志。

### 可直接复用的异常聚合器实现

线程安全，支持多线程调用，适合工业多采集线程场景：

csharp:

```c#
/// <summary>
/// 异常日志聚合器：同类型异常在时间窗口内只输出一次，避免高频刷屏
/// </summary>
public class ExceptionLogAggregator
{
    private readonly Dictionary<string, AggregateItem> _cache = new();
    private readonly int _windowSeconds = 60; // 默认60秒窗口
    private readonly object _lock = new();

    private class AggregateItem
    {
        public int Count { get; set; }
        public DateTime FirstTime { get; set; }
        public string LastMessage { get; set; }
    }

    public void LogError(string errorKey, string message, Exception ex = null)
    {
        lock (_lock)
        {
            DateTime now = DateTime.Now;
            
            if (_cache.TryGetValue(errorKey, out var item))
            {
                // 在窗口内：只计数，不打日志
                if ((now - item.FirstTime).TotalSeconds < _windowSeconds)
                {
                    item.Count++;
                    item.LastMessage = message;
                    return;
                }
                
                // 窗口过期：输出上一轮汇总
                Log.Warning("[聚合] {Key} 过去{Sec}秒内共发生{Count}次，最后一次：{Msg}", 
                    errorKey, _windowSeconds, item.Count, item.LastMessage);
            }
            
            // 首次出现或窗口重置：系统异常才打堆栈，业务异常只打消息
            if (ex != null && IsSystemException(ex))
            {
                Log.Error(ex, message);
            }
            else
            {
                Log.Warning(message);
            }
            
            _cache[errorKey] = new AggregateItem
            {
                Count = 1,
                FirstTime = now,
                LastMessage = message
            };
        }
    }

    // 判断是否为系统级异常，只有这类才输出堆栈
    private bool IsSystemException(Exception ex)
    {
        return ex is NullReferenceException 
            or IndexOutOfRangeException 
            or IOException 
            or OutOfMemoryException;
    }

    // 故障恢复时调用，输出恢复日志并清空计数
    public void MarkRecovered(string errorKey, string recoverMessage)
    {
        lock (_lock)
        {
            if (_cache.TryGetValue(errorKey, out var item))
            {
                Log.Information("{Key} 已恢复，本次持续{Duration}，共发生{Count}次：{Msg}",
                    errorKey, DateTime.Now - item.FirstTime, item.Count, recoverMessage);
                _cache.Remove(errorKey);
            }
        }
    }
}
```

#### 使用示例

csharp:

```c#
private readonly ExceptionLogAggregator _commErrorAggregator = new();

void PlcCommunication_Error(object sender, CommunicationErrorEventArgs e)
{
    // 用"PLC_通信超时"作为聚合key，同一种错误60秒内只打1次
    _commErrorAggregator.LogError(
        "PLC_通信超时", 
        $"PLC通信超时，地址:{e.Address}", 
        e.Exception);
}

void PlcCommunication_Connected(object sender, EventArgs e)
{
    // 连接恢复时输出恢复日志
    _commErrorAggregator.MarkRecovered("PLC_通信超时", "通信已恢复");
}
```

## 四、写入与格式化优化：降低 IO 与 GC 开销

### 1. 异常日志必须走异步写入

异常往往发生在系统高负载、业务压力大的时刻，如果此时同步写日志，会进一步阻塞业务线程，放大故障影响。

- 所有异常日志必须走异步队列写入，异常发生时仅入队立即返回，后台线程批量落盘；
- 异常日志优先级可设置高于普通日志，确保优先写入，但绝对不能同步阻塞业务线程。

### 2. 用框架原生异常参数，禁止手动 ToString

不要自己提前调用`ex.ToString()`拼接字符串，直接把异常对象传给日志框架：

- 框架会做格式化优化，性能远高于手动拼接；
- 如果日志级别不满足，框架根本不会执行格式化，零开销。

csharp:

```c#
// ❌ 错误：提前ToString，不管级别开不开都会执行格式化，产生大量临时字符串
Log.Error("发生异常：" + ex.ToString());

// ✅ 正确：把异常对象作为第一个参数传给框架，按需格式化
Log.Error(ex, "处理数据失败，批次号:{BatchNo}", batchNo);
```

### 3. 禁止随异常序列化大对象

异常时把完整业务对象、DataTable、全量参数转成 JSON 打日志，是非常常见的坏习惯：

- 序列化是 CPU 密集操作，大对象单次序列化可达毫秒级；
- 大字符串直接进入大对象堆，触发 Full GC，造成程序长时间停顿。
- 正确做法：异常日志只记录关键字段（ID、错误码、时间），全量数据排查做成独立的诊断包导出功能。

### 4. 延迟求值：级别不满足就不做任何计算

和普通日志一样，低级别异常日志要先判断级别，再执行格式化、序列化等耗时操作。

csharp:

```c#
// ❌ 浪费：就算Warning关闭，异常对象的格式化、序列化也已经执行了
Log.Warning(ex, "处理失败，详细数据:{Data}", JsonSerializer.Serialize(data));

// ✅ 正确：先判断级别，再执行耗时操作
if (Log.IsEnabled(LogEventLevel.Warning))
{
    string detail = JsonSerializer.Serialize(data);
    Log.Warning(ex, "处理失败，详细数据:{Data}", detail);
}
```

## 五、统一收口：避免重复记录与分散处理

### 1. 遵循「谁最终处理，谁打日志」原则

最常见的浪费：每层 catch 都打一次日志，然后继续向上抛，导致同一个异常重复输出 N 次，既浪费性能又干扰排查。

- 中间层：只做异常包装、补充上下文，不打日志；
- 最上层（UI 层、业务入口）：最终处理异常（弹窗、重试、降级）的地方，统一打一次日志。

csharp:

```c#
// ❌ 反例：每层都打日志，重复输出
void A() { try { B(); } catch(Exception ex) { Log.Error(ex); throw; } }
void B() { try { C(); } catch(Exception ex) { Log.Error(ex); throw; } }
void C() { throw new Exception("出错了"); }

// ✅ 正确：底层只抛不记，顶层统一处理统一记录
void DataAccessLayer.Query()
{
    try { /* 数据库操作 */ }
    catch (SqlException ex)
    {
        // 只包装补充上下文，不打日志
        throw new DataQueryException("查询生产数据失败", ex);
    }
}

void UI_QueryButton_Click(object sender, RoutedEventArgs e)
{
    try
    {
        var data = DataAccessLayer.Query();
        dataGrid.ItemsSource = data;
    }
    catch (Exception ex)
    {
        // 最终处理：只在这里打一次日志 + 弹窗提示
        Log.Error(ex, "查询生产数据失败");
        MessageBox.Show($"查询失败：{ex.Message}", "错误", MessageBoxButton.OK, MessageBoxImage.Error);
    }
}
```

### 2. 全局异常统一处理，一处兜底

利用 WPF 框架的全局异常钩子，集中捕获未处理异常，避免到处写零散的 try-catch 打日志。

csharp:

```c#
public App()
{
    // UI线程未处理异常
    DispatcherUnhandledException += App_DispatcherUnhandledException;
    // 非UI线程未处理异常
    AppDomain.CurrentDomain.UnhandledException += CurrentDomain_UnhandledException;
    // Task未观察到的异常
    TaskScheduler.UnobservedTaskException += TaskScheduler_UnobservedTaskException;
}

private void App_DispatcherUnhandledException(object sender, DispatcherUnhandledExceptionEventArgs e)
{
    // 统一记录系统异常，带完整堆栈
    Log.Fatal(e.Exception, "程序发生未处理UI异常");
    MessageBox.Show($"程序发生异常：{e.Exception.Message}\n请联系管理员", "错误", 
        MessageBoxButton.OK, MessageBoxImage.Error);
    e.Handled = true;
}
```

## 六、工业场景专项优化

1. **设备通信链路**：正常重连、瞬时超时不打异常日志，重试超过阈值再告警；原始报文异常单独做开关，排查问题时才开启。
2. **数据采集链路**：单次采集失败不抛异常，用失败计数统计，连续失败 N 次再触发告警，避免瞬时抖动刷屏。
3. **批量处理场景**：几万条数据批量处理时，不要每条失败都抛异常，用失败计数 + 汇总报告，最后输出一条总结日志。
4. **WPF UI 线程**：UI 层异常捕获后立即释放 UI 线程，日志写入放后台线程，避免界面卡死。

## 优化优先级总结

| 优先级    | 优化手段                                   | 性能收益       | 实施成本 |
| :-------- | :----------------------------------------- | :------------- | :------- |
| 1（最高） | 业务预期失败改用返回值，从根源减少异常抛出 | 数量级下降     | 中       |
| 2         | 高频重复异常做时间窗口聚合                 | 90%+ 下降      | 低       |
| 3         | 业务异常只记消息，不输出堆栈               | 数倍下降       | 极低     |
| 4         | 异常日志异步写入，不阻塞业务线程           | 显著降低阻塞   | 极低     |
| 5         | 统一收口，消除重复日志                     | 按重复倍数下降 | 低       |

对于工业软件而言，绝大多数异常都属于「业务预期内的失败」，通过返回值模式 + 聚合去重，就能把异常日志的性能影响降到几乎可忽略的程度，同时保留真正系统故障的完整排查信息。
