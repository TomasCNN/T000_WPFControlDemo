# 999999009-17_工业上位机日志内容规范（工业视觉 / 工控场景通用）

工业上位机日志的核心价值是**故障可追溯、生产可审计、性能可分析**，和普通业务软件日志最大的区别是：强调时序精度、现场上下文、操作可审计，同时不能因日志影响设备实时性。

以下从通用格式、分级规则、场景细则、编写原则、红线禁令五个维度，给出可直接落地的内容规范。

------

## 一、日志条目通用内容规范

所有日志条目遵循「核心字段必填 + 业务字段按需扩展」的原则，保证单条日志既能看懂事件本身，也能关联到具体生产 / 设备上下文。

### 1. 必填核心字段（每条日志必须包含）

| 字段         | 规范要求                                                     | 作用                                                         |
| :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **时间戳**   | 精确到毫秒，统一使用 `yyyy-MM-dd HH:mm:ss.fff` 格式，使用工控机本地时间 | 工业设备动作周期短，毫秒级精度才能还原事件先后顺序，排查时序类问题 |
| **日志级别** | 统一使用 `DEBUG / INFO / WARN / ERROR / FATAL` 五级大写标识  | 快速过滤严重程度，生产环境可直接按级别筛选                   |
| **模块名称** | 明确归属模块，如「线扫相机」「PLC 通信」「检测算法」「MES 交互」 | 快速定位问题所属模块，不用通读全文                           |
| **线程 ID**  | 记录当前执行线程的编号                                       | 排查多线程并发、死锁、时序错乱问题的核心依据                 |
| **事件描述** | 清晰说明发生了什么事、结果如何、关键参数是什么               | 日志主体，要求具体可定位                                     |
| **异常堆栈** | `ERROR` / `FATAL` 级别必须附带完整 `Exception` 堆栈信息      | 只打错误消息等于没打，堆栈才能定位到具体代码行               |

### 2. 可选业务扩展字段（工业场景追溯必备）

根据日志类型补充上下文，保证问题可追溯到具体产品、批次、工位：

- 产品标识：产品 SN、批次号、工单编号
- 设备维度：工位号、设备编号、相机 / 轴号
- 任务标识：帧序号、检测任务 ID、通信流水号
- 操作主体：操作员工号、登录用户名

### 3. 格式统一要求

1. 整条日志字段分隔统一，推荐使用 `|` 分隔，人类可读、程序也易解析；
2. 文件编码统一使用 UTF-8，避免工控机不同语言环境乱码；
3. 单条日志控制在一行内，异常堆栈可换行但要缩进，便于工具检索。

**合格示例**：

plaintext:

```tex
2026-06-23 14:25:30.125 | INFO  | 线程12 | 线扫相机 | 相机初始化成功，分辨率4096*2048，帧率100fps
2026-06-23 14:25:31.456 | ERROR | 线程12 | 线扫相机 | 第1234帧取图超时，超时设置500ms
   System.TimeoutException: 等待图像就绪超时
   at ImageHelper.GetBitmap() 位置 D:\Project\ImageHelper.cs:第85行
```

## 二、分级日志内容规范

不同级别有明确的内容边界，禁止越级打印：该打错误的不能只打警告，该调试的不能刷信息日志刷屏。

### 1. FATAL（致命错误）

- **适用场景**：程序崩溃、紧急停机、系统级故障，设备无法继续运行

- **内容要求**：必须记录故障发生时的核心现场状态（当前工位、运行模式、已加工数量）、完整异常堆栈、故障触发源

- **示例**：

  plaintext:

  ```tex
  2026-06-23 15:10:00.003 | FATAL | 线程1 | 主程序 | 程序未捕获异常触发紧急停机，当前批次B2026062301，已加工125件
     System.OutOfMemoryException: 内存不足
     at MainWindow.ProcessFrame()
  ```

### 2. ERROR（功能错误）

- **适用场景**：单个功能模块失效，影响当前生产，单功能不可用；设备本身未停机，但对应工位无法正常工作
- **内容要求**：必须说明哪个功能失败、失败原因、关键入参、完整异常堆栈；禁止只写「出错了」「失败了」
- **正例**：`PLC写入M100地址失败，写入值1，错误码：0x05，连接状态：已连接`
- **反例**：`PLC出错了`（无模块、无原因、无参数，完全无效）

### 3. WARN（警告）

- **适用场景**：单次异常、参数临近阈值、重试成功、资源积压，不影响当前运行，但存在隐患
- **内容要求**：必须说明当前值、阈值 / 正常值、潜在影响；用于提前发现问题，避免演变成错误
- **正例**：`图像队列积压，当前队列长度15，警戒值10，存在丢帧风险`
- **反例**：`队列有点长`（无量化、无阈值，无法判断严重程度）

### 4. INFO（信息）

- **适用场景**：正常运行的关键节点、状态切换、流程里程碑；用于还原设备运行轨迹
- **内容要求**：只记关键节点，禁止在高频循环内打印；记录状态变化的前后值
- **正例**：`切换至自动模式，当前批次号B2026062301` `检测算法加载完成，模板数量12个`
- **禁止**：相机 100fps 回调里每帧打 Info、循环内逐次打印，会刷爆磁盘且无实际价值

### 5. DEBUG（调试）

- **适用场景**：开发调试、现场排查问题用的细节信息、中间变量值、逐帧数据
- **内容要求**：详细记录中间过程、变量值；**生产环境默认关闭**，仅排查问题时临时开启
- **示例**：`第1234帧图像宽高4096*2048，算法定位结果X=123.45，Y=67.89`

## 三、核心业务场景内容细则（工业上位机专属）

针对工业上位机最常见的 5 类场景，明确必须记录的信息和禁止行为。

### 1. 设备通信类（相机、PLC、运动控制、MES 交互）

这是上位机问题最高发的区域，日志必须能完整还原通信交互过程。

- **必须记录**：

  1. 连接 / 断开事件：时间、设备地址、连接结果、失败原因
  2. 读写失败：地址 / 指令、发送值、返回错误码、重试次数
  3. 超时事件：超时阈值、实际等待时长、当前连接状态

- **正例**：

  plaintext:

  ```tex
  线扫相机1取图超时，超时设置500ms，帧序号1234，相机心跳状态正常
  PLC读取D200地址失败，错误码0x07，从站地址1，已重试第2次
  ```

- **禁止**：只打印「通信失败」，不附地址、错误码、重试信息

### 2. 生产流程类

用于生产追溯，还原产品加工全流程。

- **必须记录**：
  1. 批次开始 / 结束：批次号、产品型号、计划数量
  2. 单件检测结果：SN 号、OK/NG、NG 类型、检测耗时
  3. 模式切换：手动 / 自动、运行 / 暂停，切换操作人
- **正例**：`产品SN2026062300125检测完成，结果NG，缺陷类型：划痕，检测耗时12ms`

### 3. 操作审计类（满足合规审计要求）

所有人工干预、参数修改必须留痕，是医药、食品、3C 等行业的硬性要求。

- **必须记录**：

  1. 操作人：工号 / 用户名
  2. 操作对象：哪个参数、哪个设备
  3. 修改前后的值：旧值 → 新值
  4. 操作时间、操作结果

- **正例**：

  plaintext:

  ```tex
  操作员001 修改检测阈值，旧值0.85，新值0.90，修改成功
  操作员002 手动复位报警A001，复位成功
  ```

- **禁止**：只记录「修改了参数」，不记改前改后值，等于没留痕

### 4. 性能监控类

对应你优化 CT、排查卡顿的需求，用于定位性能瓶颈。

- **必须记录**：
  1. 耗时类：取图总耗时、算法处理耗时、通信耗时，带具体毫秒值
  2. 资源类：队列长度、内存占用、GDI 对象数量、CPU 使用率
  3. 统计类：分钟 / 小时产量、帧率、丢帧数量
- **正例**：`线扫取图总耗时3.2ms，其中等待图像2.1ms，拷贝1.1ms`

### 5. 报警与安全类

- **必须记录**：报警代码、报警文本、触发时间、触发时设备状态、复位时间、复位人
- **正例**：`触发安全门打开报警A003，当前运行模式：自动，触发时间14:30:00.123`

## 四、日志内容编写核心原则

### 1. 具体可定位，禁止模糊表述

- ❌ 错误：`相机有问题`
- ✅ 正确：`线扫相机1取图连续超时3次，超时阈值500ms`

### 2. 量化可对比，带数值不带形容词

- ❌ 错误：`队列很长、延迟很高`
- ✅ 正确：`图像队列长度20，超过警戒值10`

### 3. 一事一条，不堆砌信息

一条日志只说一件事，不要把多个操作、多个模块的信息揉在一条里，不利于检索过滤。

### 4. 结果闭环，操作必带结果

有操作就要有结果，成功 / 失败都要说明，不能只发请求不记响应。

- 示例：`下发启动指令成功，PLC返回ACK`

### 5. 上下文完整，可串联事件

关键日志带上业务 ID（帧序号、SN 号），可以通过 ID 把一条产品的取图、检测、结果上报日志全部串联起来。

------

## 五、绝对禁止写入日志的内容（红线）

1. **核心敏感数据**：产品核心工艺参数、保密配方、客户信息，防止泄密；
2. **账号密码 / 密钥**：数据库密码、PLC 密码、接口密钥、权限令牌；
3. **大容量二进制数据**：图像像素数组、完整文件流，会让日志文件极速膨胀；
4. **无意义刷屏日志**：高频循环内逐次打印、重复的相同内容，既占磁盘又无价值；
5. **人身攻击、脏话、调试临时吐槽**；
6. **未脱敏的个人隐私信息**：身份证号、手机号等。

## 六、一条合格的工业日志示例

plaintext:

```tex
2026-06-23 14:30:15.678 | ERROR | 线程15 | PLC通信 | 写入地址M100失败，写入值1，从站地址1，错误码0x05，第1次重试
   System.IO.IOException: 通信异常，从站无响应
   at PlcClient.Write(string address, short value) 位置 PlcClient.cs:第156行
```

这条日志包含了全部关键信息：什么时候、哪个模块、什么操作、关键参数、错误原因、代码位置，拿到日志就能直接定位问题，无需再反复到现场复现。
