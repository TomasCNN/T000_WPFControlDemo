# 003011021_WPF 项目 文件夹规范深度解析

全部结合你正在开发的**埃科线扫相机 + 西门子 PLC 视觉检测设备**场景，用你每天都会遇到的实际问题来解释每个文件夹的作用、文件类型和命名规范，所有内容均可直接落地到你的项目中。

## 问题一：详细说明各文件夹的作用（结合具体工业场景）

### 核心设计逻辑

> 数字越小，层级越低，越稳定；数字越大，层级越高，越易变。
>
> 上层只能依赖下层，下层绝对不能依赖上层。这是工业软件能够 5~10 年稳定运行、快速迭代的基础。

| 文件夹                 | 层级                 | 核心作用                                        | **线扫视觉设备具体场景阐述**                                 |
| :--------------------- | :------------------- | :---------------------------------------------- | :----------------------------------------------------------- |
| **01_Abstractions**    | 硬件抽象层（最底层） | 定义所有硬件和服务的统一接口，隔离变化          | **工业场景最核心的价值：硬件可插拔**当客户要求把埃科线扫相机换成海康面阵相机时：✅ 你只需要在`02_Implementations`中新增一个`HikCamera.cs`实现`ICamera`接口✅ 然后修改`appsettings.json`中的一行配置：`"CameraType": "Hik"`✅ 上层所有代码（`CameraService`、`DetectionProcess`、`MainViewModel`）**一行都不用改**如果没有这一层，你需要在所有用到相机的地方修改代码，至少要改几十个地方 |
| **02_Implementations** | 硬件实现层           | 不同品牌硬件的具体 SDK 调用和寄存器操作         | **所有硬件相关的 "脏代码" 都放在这里**✅ 埃科相机的 SDK 初始化、取图回调、曝光时间设置✅ 西门子 PLC 的 S7 协议连接、寄存器读写、心跳包✅ NLog 日志的初始化、文件写入、日志归档这一层是唯一允许出现硬件 SDK 代码的地方，上层永远看不到 SDK 的存在 |
| **03_Services**        | 服务层               | 封装通用能力，提供强类型、安全的 API 给上层调用 | **隐藏底层复杂性，处理通用问题**✅ `PlcService.WaitForStartTrigger()`：封装了 PLC 信号等待的分级等待逻辑（前 100ms 自旋，之后睡眠）、超时处理、异常捕获和日志记录上层调用时只需要写一行代码，不需要关心底层是怎么实现的✅ `CameraService.GetBitmap()`：封装了图像克隆、资源释放、超时保护✅ `ConfigService`：封装了 JSON 配置文件的读取和保存，提供强类型的配置对象 |
| **04_Business**        | 业务逻辑层           | 核心业务流程编排、业务规则判断、设备状态管理    | **整个系统的大脑，只做流程控制**✅ `DetectionProcess.RunAsync()`：完整的检测主流程:1. 等待 PLC 起点触发;2. 相机取图;3. 立刻发送 PLC 结束信号（CT 优化核心）;4. 算法缺陷检测;5. 保.存数据和图像.这一层不做任何具体实现，所有操作都委托给服务层✅ `StateMachine`：管理设备的空闲 / 运行 / 暂停 / 错误状态转换，防止非法操作。 |
| **05_ViewModels**      | MVVM 层              | UI 逻辑、数据绑定、命令处理、UI 状态管理        | **连接 UI 和业务的桥梁**✅ `MainViewModel`：管理主界面的开始 / 停止按钮状态、运行统计数据（总数 / OK 数 / NG 数）、状态栏消息✅ `MonitorViewModel`：接收算法模块发布的`DefectDetectedEvent`事件，更新 UI 显示缺陷列表✅ `ParameterViewModel`：处理参数配置的保存和加载这一层只处理 UI 相关逻辑，绝对不包含任何业务规则和硬件操作 |
| **06_Views**           | UI 层                | 界面布局、样式、控件、用户输入处理              | **只负责显示和用户输入**✅ `IoMonitorView.xaml`：PLC 输入输出状态监控界面，用 UniformGrid 排列 IO 点位✅ `MonitorView.xaml`：实时图像显示和缺陷标注界面✅ `ParameterView.xaml`：相机参数和算法参数配置界面这一层的.xaml.cs 文件中除了构造函数，不应该有任何其他代码 |
| **07_Models**          | 公共数据模型层       | 纯数据结构，无任何逻辑                          | **所有层都可以依赖的公共数据载体**✅ `Defect.cs`：缺陷数据结构（位置、大小、类型）✅ `ProductRecord.cs`：产品检测记录（条码、结果、检测时间、缺陷列表）✅ `AppConfig.cs`：系统配置结构（相机参数、PLC 参数、算法参数）✅ `DeviceStatus.cs`：设备状态枚举这些类只有属性，没有任何方法 |
| **08_Data**            | 数据访问层           | 数据库、文件、图像的读写操作                    | **统一管理所有数据持久化逻辑**✅ `DatabaseContext.cs`：SQLite 数据库上下文，自动创建表结构✅ `FileManager.cs`：图像文件的保存和读取，按日期自动创建文件夹✅ `DefectRepository.cs`：缺陷记录的增删改查上层不需要关心数据是存在 SQLite 还是 MySQL，也不需要关心图像存在哪个文件夹 |
| **09_Common**          | 通用工具层           | 所有模块通用的辅助类、扩展方法、转换器          | **与业务无关的通用工具，可以在任何项目中复用**✅ `ImageHelper.cs`：Bitmap 和 BitmapSource 的转换、图像缩放、裁剪✅ `BoolToColorConverter.cs`：布尔值转颜色的 WPF 转换器（用于 IO 指示灯）✅ `TimeHelper.cs`：时间格式化、耗时计算✅ `SpinWaitExtensions.cs`：SpinWait 的扩展方法这一层绝对不能引用任何业务相关的代码 |
| **Configs**            | 配置层               | 所有系统配置文件                                | **所有可配置的参数都放在这里，不需要修改代码就能调整系统行为**✅ `appsettings.json`：相机 IP、PLC IP、超时时间、数据库路径✅ `NLog.config`：日志配置（日志级别、保存路径、归档规则）✅ `PlcAddresses.json`：PLC 信号地址配置（起点触发、终点触发、报警）当现场需要修改 PLC IP 地址时，只需要修改这个文件，不需要重新编译程序 |

## 问题二：各文件夹的文件类型有哪些？

### 严格的文件类型隔离原则

> **每个文件夹只能放一种类型的文件**，绝对不允许混合职责。这是避免代码变成 "屎山" 的最有效手段。

| 文件夹                 | 允许的文件类型                             | 绝对禁止放入                             | **线扫视觉设备具体示例**                                     |
| :--------------------- | :----------------------------------------- | :--------------------------------------- | :----------------------------------------------------------- |
| **01_Abstractions**    | 接口文件 (.cs)                             | 任何实现类、任何业务逻辑、任何 UI 代码   | `ICamera.cs`、`IPlc.cs`、`ILogger.cs`、`IDataService.cs`、`IAlgorithmService.cs` |
| **02_Implementations** | 接口的具体实现类 (.cs)                     | 任何业务逻辑、任何 UI 代码               | `IkCamera.cs`、`SiemensPlc.cs`、`NLogLogger.cs`、`SqliteDataService.cs`、`SurfaceDefectDetector.cs` |
| **03_Services**        | 服务类 (.cs)                               | 任何 UI 代码、任何业务流程               | `CameraService.cs`、`PlcService.cs`、`AlgorithmService.cs`、`ConfigService.cs`、`DataService.cs` |
| **04_Business**        | 流程类、状态机类、管理器类 (.cs)           | 任何硬件操作、任何 UI 代码、任何数据访问 | `DetectionProcess.cs`、`ProductionManager.cs`、`DeviceStateMachine.cs`、`AlarmManager.cs` |
| **05_ViewModels**      | ViewModel 类 (.cs)                         | 任何硬件操作、任何业务逻辑、任何数据访问 | `MainViewModel.cs`、`MonitorViewModel.cs`、`ParameterViewModel.cs`、`IoMonitorViewModel.cs`、`DataViewModel.cs` |
| **06_Views**           | XAML 文件 + 对应的.xaml.cs 代码隐藏文件    | 任何业务逻辑、任何硬件调用、任何数据处理 | `MainWindow.xaml`、`MonitorView.xaml`、`ParameterView.xaml`、`IoMonitorView.xaml`、`DataView.xaml` |
| **07_Models**          | 纯数据实体类、DTO 类、枚举 (.cs)           | 任何方法、任何逻辑、任何依赖             | `Defect.cs`、`ProductRecord.cs`、`AppConfig.cs`、`DeviceStatus.cs`、`AlarmLevel.cs` |
| **08_Data**            | 数据库上下文、文件管理器、数据仓储类 (.cs) | 任何业务逻辑、任何 UI 代码               | `DatabaseContext.cs`、`FileManager.cs`、`DefectRepository.cs`、`ImageSaver.cs`、`ConfigRepository.cs` |
| **09_Common**          | 转换器、扩展方法、帮助类、常量类 (.cs)     | 任何业务相关代码                         | `BoolToColorConverter.cs`、`BitmapExtensions.cs`、`ImageHelper.cs`、`TimeHelper.cs`、`PlcAddressConstants.cs` |
| **Configs**            | 配置文件 (.json、.config、.xml)            | 任何代码文件                             | `appsettings.json`、`NLog.config`、`PlcAddresses.json`、`CameraParams.json`、`AlgorithmParams.json` |

### 子文件夹组织规范

当某个文件夹下的文件超过 10 个时，按功能拆分子文件夹，保持同一层级的文件数量不超过 15 个：

plaintext

```tex
02_Implementations/
├── Cameras/                  # 所有相机实现
│   ├── IkCamera.cs
│   ├── HikCamera.cs
│   └── BaslerCamera.cs
├── Plcs/                     # 所有PLC实现
│   ├── SiemensPlc.cs
│   ├── OmronPlc.cs
│   └── MitsubishiPlc.cs
├── Algorithms/               # 所有算法实现
│   ├── SurfaceDefectDetector.cs
│   └── DimensionDetector.cs
└── Loggers/                  # 所有日志实现
    └── NLogLogger.cs

06_Views/
├── MonitorView/              # 实时监控模块
│   ├── MonitorView.xaml
│   └── MonitorView.xaml.cs
├── ParameterView/            # 参数配置模块
│   ├── CameraParameterView.xaml
│   ├── AlgorithmParameterView.xaml

    ├── IoMonitorView.xaml
    └── IoMonitorView.xaml.cs
```

## 问题三：命名规范有哪些？

### 核心命名原则

> **清晰性优先，简洁性其次**。命名要能准确反映文件的职责，让开发者看到名字就知道这个文件是做什么的，不需要看代码。

### 一、文件夹命名规范

| 类型     | 规范                              | 示例                                                   |
| :------- | :-------------------------------- | :----------------------------------------------------- |
| 根文件夹 | `两位数字_英文名称`，帕斯卡命名法 | `01_Abstractions`、`02_Implementations`、`03_Services` |
| 子文件夹 | 英文名称，帕斯卡命名法，复数形式  | `Cameras`、`Plcs`、`Converters`、`Extensions`          |

**数字前缀说明**：

- 必须是两位数字，不足两位前面补 0
- 数字间隔为 1，方便以后插入新的层级（比如在 02 和 03 之间插入 02.5_Adapters）
- 数字越小，层级越低，越稳定

### 二、文件命名规范

| 文件夹             | 命名规范                                           | 线扫视觉设备示例                                             |
| :----------------- | :------------------------------------------------- | :----------------------------------------------------------- |
| 01_Abstractions    | `I+功能名称.cs`，前缀 I 表示接口                   | `ICamera.cs`、`IPlc.cs`、`IAlgorithmService.cs`              |
| 02_Implementations | `品牌+功能名称.cs`，帕斯卡命名法                   | `IkCamera.cs`、`SiemensPlc.cs`、`NLogLogger.cs`              |
| 03_Services        | `功能名称+Service.cs`，后缀 Service 表示服务类     | `CameraService.cs`、`PlcService.cs`、`ConfigService.cs`      |
| 04_Business        | `功能名称+Process/Manager/StateMachine.cs`         | `DetectionProcess.cs`、`ProductionManager.cs`、`DeviceStateMachine.cs` |
| 05_ViewModels      | `功能名称+ViewModel.cs`，后缀 ViewModel            | `MainViewModel.cs`、`MonitorViewModel.cs`、`IoMonitorViewModel.cs` |
| 06_Views           | `功能名称+View.xaml`，后缀 View 表示界面           | `MonitorView.xaml`、`ParameterView.xaml`、`IoMonitorView.xaml` |
| 07_Models          | `实体名称.cs`，帕斯卡命名法                        | `Defect.cs`、`ProductRecord.cs`、`AppConfig.cs`              |
| 08_Data            | `功能名称+Context/Manager/Repository.cs`           | `DatabaseContext.cs`、`FileManager.cs`、`DefectRepository.cs` |
| 09_Common          | `功能名称+Converter/Extension/Helper/Constants.cs` | `BoolToColorConverter.cs`、`BitmapExtensions.cs`、`ImageHelper.cs`、`PlcAddressConstants.cs` |

### 三、类和方法命名规范

| 类型 | 规范                              | 线扫视觉设备示例                                          |
| :--- | :-------------------------------- | :-------------------------------------------------------- |
| 类   | 帕斯卡命名法，名词或名词短语      | `CameraService`、`DetectionProcess`、`Defect`             |
| 接口 | 前缀 I + 帕斯卡命名法             | `ICamera`、`IPlc`、`IDataService`                         |
| 方法 | 帕斯卡命名法，动词或动词短语      | `GetBitmap()`、`WaitForStartTrigger()`、`DetectDefects()` |
| 属性 | 帕斯卡命名法，名词或名词短语      | `ExposureTimeUs`、`IsRunning`、`TotalCount`               |
| 事件 | 帕斯卡命名法，动词 + 过去分词后缀 | `DefectDetected`、`ProcessCompleted`、`StatusChanged`     |

### 四、工业场景特殊命名规范（必须遵守）

1. **硬件相关命名必须带品牌前缀**

   

   - ✅ `IkCamera`、`SiemensPlc`
   - ❌ `Camera`、`Plc`（不知道是哪个品牌的）

   

2. **PLC 地址绝对不能用魔法字符串**

   

   csharp：

   ```c#
   // ✅ 正确：定义常量集中管理
   public static class PlcAddressConstants
   {
       public const string StartTrigger = "M100";
       public const string EndTrigger = "D200";
       public const string Alarm = "M200";
   }
   
   // 调用
   _plc.WriteShort(PlcAddressConstants.EndTrigger, 3);
   
   // ❌ 错误：魔法字符串散落在代码中
   _plc.WriteShort("D200", 3);
   ```

   

3. **事件命名必须用过去分词**

   

   - ✅ `DefectDetectedEvent`（缺陷已检测到）
   - ✅ `ProcessCompletedEvent`（流程已完成）
   - ❌ `DetectDefectEvent`、`CompleteProcessEvent`

   

4. **布尔值命名必须用 is/has/can 前缀**

   

   - ✅ `IsRunning`、`HasDefect`、`CanStart`
   - ❌ `Running`、`Defect`、`Start`

## 工业项目最佳实践总结

1. **代码审查第一关：文件位置检查**：在代码审查时，首先检查文件是否放在了正确的文件夹中。这是最容易执行也是最有效的规范。
2. **新人培训第一节课：项目结构**：让每个新人在写第一行代码之前，就清楚每个文件夹应该放什么文件，以及为什么要这么放。
3. **所有配置都要放在 Configs 文件夹**：绝对不要在代码中硬编码任何参数，包括 IP 地址、端口号、超时时间、文件路径等。
4. **定期清理无效文件**：删除不再使用的文件和代码，保持项目结构整洁。
5. **不要随意新增根文件夹**：如果需要新增根文件夹，必须经过团队讨论，确保符合分层架构原则。
