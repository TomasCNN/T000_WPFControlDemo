# 999999009-2_避免异常日志滥用的完整方案（工业软件 / WPF 场景适配）

异常日志滥用是工业软件性能卡顿、日志爆炸、排查困难的核心原因之一，本质是混淆了 **「系统非预期错误」**和**「业务预期内失败」** 的边界。异常的捕获、堆栈解析、格式化开销是普通 Info 日志的几十到上百倍，高频滥用会快速占满 CPU 和磁盘 IO，同时淹没真正有价值的错误信息。

以下从设计、编码、框架、运维四个层面，结合工业上位机、设备通信、数据采集等典型场景，给出可直接落地的规避方法。

------

## 一、从设计根源划清边界：异常只用于「非预期系统错误」

### 核心原则

**异常是给程序员排查 bug 用的，不是用来控制业务流程的。**

预期内的业务失败（比如通信超时、参数超限、设备忙、数据为空）都属于正常业务分支，不该通过抛异常 + 打日志来处理。

### 工业场景典型滥用反例

- PLC 通信超时、设备未就绪、传感器数据校验不通过，全部用抛异常处理；
- 用异常跳出循环、做条件判断，把异常当 `goto` 用；
- 用户输入格式错误、权限不足，也抛异常并打完整堆栈。

### 正确做法

1. **明确划分两类失败**

   | 类型             | 定义                                                         | 处理方式                          | 是否打异常日志                     |
   | :--------------- | :----------------------------------------------------------- | :-------------------------------- | :--------------------------------- |
   | **系统异常**     | 非预期、代码 bug 导致的错误（空引用、索引越界、文件损坏、内存不足） | 抛异常，上层捕获处理              | 必须打完整堆栈                     |
   | **业务预期失败** | 正常流程中可能出现的失败（通信超时、参数超限、设备忙、无数据） | 返回状态码 / 结果对象，走正常分支 | 打 Info/Warning 普通日志，不打堆栈 |

2. **状态机优先于异常**

   设备通信、流程控制类场景，用状态机管理运行状态（连接中、运行中、暂停、故障），状态切换时打普通日志，不要用异常驱动状态流转。

## 二、分级记录：不是所有异常都需要完整堆栈

### 核心原则

根据异常的严重程度和类型，决定日志粒度，杜绝「不管什么异常都打 `ex.ToString()` 全堆栈」的偷懒写法。

### 分级策略

1. **致命错误（Fatal）**：程序崩溃、核心功能不可用（数据库连不上、配置文件损坏）
   - 记录：完整堆栈 + 上下文信息（时间、模块、参数）+ 系统环境
   - 保留：长期留存，用于根因分析
2. **系统错误（Error）**：功能异常、非预期失败（空引用、类型转换失败、文件读写失败）
   - 记录：异常类型 + 错误消息 + 堆栈跟踪 + 关键上下文
   - 保留：中期留存，用于修复 bug
3. **业务异常（Warning）**：预期内的业务失败（参数超限、设备忙、校验不通过）
   - 记录：仅错误码 + 错误描述，**不打堆栈**
   - 保留：短期留存，用于业务审计
4. **可恢复异常（Info）**：瞬时、可自动重试恢复的异常（单次通信超时、网络抖动）
   - 记录：仅计数或简要提示，不单独打异常日志
   - 重试多次仍失败再升级为 Warning/Error

### 代码示例：业务异常不打堆栈

csharp：

```c#
// ❌ 滥用：业务预期失败也打完整堆栈，性能差且无意义
try
{
    plc.WriteTemperature(targetTemp);
}
catch (DeviceBusyException ex)
{
    Log.Error(ex, "设备忙，写入温度失败"); // 打印完整堆栈，完全没必要
    throw;
}

// ✅ 正确：业务异常只打错误信息，不输出堆栈
try
{
    plc.WriteTemperature(targetTemp);
}
catch (DeviceBusyException ex)
{
    Log.Warning("设备忙，写入温度失败，错误码：{Code}，消息：{Msg}", 
        ex.ErrorCode, ex.Message); // 仅记录关键信息
}
```

## 三、高频异常聚合去重：避免重复刷屏与性能损耗

### 核心问题

工业场景最常见的滥用：设备断连、通信超时类异常每秒触发几十上百次，每条都打完整堆栈，瞬间刷爆日志文件，同时占满 CPU。

### 解决方案：滑动窗口聚合 + 变更触发

同一类异常在固定时间窗口内只记录一次，同时统计次数，窗口结束输出汇总；状态恢复时再打一条恢复日志。

#### 代码示例：异常聚合器

csharp:

```c#
/// <summary>
/// 异常日志聚合器：同一类异常N秒内只输出一次，避免高频刷屏
/// </summary>
public class ExceptionLogAggregator
{
    private readonly Dictionary<string, (int Count, DateTime FirstTime)> _cache = new();
    private readonly int _windowSeconds = 60; // 60秒窗口
    private readonly object _lock = new();

    public void LogError(string errorKey, string message, Exception ex = null)
    {
        lock (_lock)
        {
            DateTime now = DateTime.Now;
            
            if (_cache.TryGetValue(errorKey, out var item))
            {
                // 在窗口内：只计数，不打日志
                if ((now - item.FirstTime).TotalSeconds < _windowSeconds)
                {
                    _cache[errorKey] = (item.Count + 1, item.FirstTime);
                    return;
                }
                
                // 窗口过期：输出上一轮汇总，重置计数
                Log.Warning("[聚合] {Key} 过去{Sec}秒内共发生{Count}次：{Msg}", 
                    errorKey, _windowSeconds, item.Count, message);
            }
            
            // 首次出现或窗口重置：打一条完整日志（严重异常才打堆栈）
            if (ex != null && IsCriticalException(ex))
            {
                Log.Error(ex, message);
            }
            else
            {
                Log.Warning(message);
            }
            
            _cache[errorKey] = (1, now);
        }
    }
    
    private bool IsCriticalException(Exception ex)
    {
        // 系统级异常才打堆栈，业务异常不打
        return ex is NullReferenceException or IndexOutOfRangeException or IOException;
    }
}
```

### 工业场景最佳实践

- 设备通信异常：断连时打 1 次告警，重连成功打 1 次恢复，中间重连失败只计数不打日志；
- 数据采集超限：超阈值瞬间打 1 次告警，持续超限期间不重复打，恢复正常打 1 次恢复通知。

## 四、规范异常处理链路：谁最终处理，谁打日志

### 核心问题：重复打日志

最常见的滥用之一：每层 catch 都打一次日志，然后继续往上抛，导致同一个异常在日志里重复出现 N 次，既浪费性能又干扰排查。

csharp:

```c#
// ❌ 反例：每层都打日志，重复输出
void A() { try { B(); } catch(Exception ex) { Log.Error(ex); throw; } }
void B() { try { C(); } catch(Exception ex) { Log.Error(ex); throw; } }
void C() { throw new Exception("出错了"); }
```

### 规范原则

1. **单一记录原则**：一个异常只在最终处理它的地方打一次日志，中间层只负责传播、不负责记录；
2. **谁处理谁打日志**：比如 UI 层捕获异常给用户弹窗、业务层重试成功、底层吞掉异常并降级，这些「最终处理」的地方才打日志；
3. **向上抛异常时，不要重新 new 异常**，保留原始堆栈，除非需要补充上下文信息。

### 正确示例

csharp:

```c#
// 数据访问层：只抛异常，不打日志，因为它不负责最终处理
public DataTable QueryProductionData(DateTime date)
{
    try
    {
        // 数据库操作...
    }
    catch (SqlException ex)
    {
        // 包装异常，补充业务上下文，不打日志
        throw new DataQueryException($"查询{date:yyyy-MM-dd}生产数据失败", ex);
    }
}

// UI/业务层：最终处理异常，统一打日志
private void QueryButton_Click(object sender, RoutedEventArgs e)
{
    try
    {
        var data = QueryProductionData(queryDatePicker.SelectedDate.Value);
        dataGrid.ItemsSource = data;
    }
    catch (Exception ex)
    {
        // 最终处理：打日志 + 弹窗提示用户
        Log.Error(ex, "查询生产数据失败");
        MessageBox.Show($"查询失败：{ex.Message}", "错误", MessageBoxButton.OK, MessageBoxImage.Error);
    }
}
```

### 补充：禁止「空吞异常」

另一种滥用是 catch 住异常只打日志，不做任何处理，假装问题不存在。打日志不等于处理异常，要么恢复、要么重试、要么上报用户，三者必居其一。

## 五、用「返回结果模式」替代预期内失败的异常抛出

### 核心思想

对于预期内可能失败的操作，用**返回结果对象**代替异常，从根源上消除不必要的异常日志。这是工业软件最推荐的做法，尤其适合设备通信、参数校验、数据读取这类高频且失败率高的场景。

### 两种实现方式

#### 1. Try-Parse 模式（简单场景）

用 `bool` 返回值表示是否成功，`out` 参数返回结果，完全不抛异常。

csharp:

```c#
// ✅ 工业场景常用：读取PLC数据，成功返回true，失败返回false
public bool TryReadTemperature(out double temperature)
{
    temperature = 0;
    try
    {
        if (!plc.IsConnected) return false;
        
        temperature = plc.ReadDouble("DB1.DBD0");
        return true;
    }
    catch
    {
        // 内部静默处理，不向外抛异常，调用方通过返回值判断
        return false;
    }
}

// 调用方：走正常分支，无异常开销
if (plc.TryReadTemperature(out var temp))
{
    temperatureText.Text = $"{temp:F1}℃";
}
else
{
    temperatureText.Text = "--";
}
```

#### 2. Result<T> 结果对象（复杂场景）

自定义通用结果类，包含成功状态、错误信息、错误码，适合需要返回失败详情的场景。

csharp:

```c#
public class Result<T>
{
    public bool IsSuccess { get; }
    public T Data { get; }
    public string ErrorMessage { get; }
    public int ErrorCode { get; }

    private Result(bool isSuccess, T data, string errorMsg, int errorCode)
    {
        IsSuccess = isSuccess;
        Data = data;
        ErrorMessage = errorMsg;
        ErrorCode = errorCode;
    }

    public static Result<T> Success(T data) => new(true, data, string.Empty, 0);
    public static Result<T> Fail(string msg, int code = -1) => new(false, default, msg, code);
}

// 使用
public Result<double> CalculateYieldRate(string batchNo)
{
    if (string.IsNullOrEmpty(batchNo))
        return Result<double>.Fail("批次号不能为空", 1001);
    
    var data = GetBatchData(batchNo);
    if (data == null)
        return Result<double>.Fail("批次不存在", 1002);
    
    double yield = data.GoodCount / data.TotalCount;
    return Result<double>.Success(yield);
}
```

> 收益：预期内的失败完全走普通对象返回，无异常抛出、无堆栈解析、无异常日志，性能提升显著，代码流程也更清晰。

## 六、框架层统一收口：全局异常处理 + 日志限流兜底

### 1. 全局异常统一处理

不要在业务代码里到处写 `try-catch` 打日志，利用框架提供的全局异常过滤器，统一捕获未处理的异常，集中记录日志。

#### WPF 全局异常处理

csharp:

```c#
public App()
{
    // UI线程未处理异常
    DispatcherUnhandledException += App_DispatcherUnhandledException;
    
    // 非UI线程未处理异常
    AppDomain.CurrentDomain.UnhandledException += CurrentDomain_UnhandledException;
    
    // Task未观察到的异常
    TaskScheduler.UnobservedTaskException += TaskScheduler_UnobservedTaskException;
}

private void App_DispatcherUnhandledException(object sender, DispatcherUnhandledExceptionEventArgs e)
{
    // 统一记录系统异常，带完整堆栈
    Log.Fatal(e.Exception, "程序发生未处理UI异常");
    
    // 友好提示用户
    MessageBox.Show($"程序发生异常：{e.Exception.Message}\n请联系管理员", "错误", 
        MessageBoxButton.OK, MessageBoxImage.Error);
    
    e.Handled = true; // 防止程序直接崩溃
}
```

### 2. 日志框架层面做限流与抑制

利用 Serilog/NLog 等框架的过滤、抑制功能，从底层限制异常日志的输出频率：

- 同一来源、同一类型的异常，单位时间内最多输出 N 条；
- 对重复异常自动折叠，只保留第一条和最后一条；
- 业务异常类默认不输出堆栈，系统异常才输出。

#### Serilog 异常过滤示例

csharp:

```c#
Log.Logger = new LoggerConfiguration()
    // 过滤掉业务异常的堆栈输出
    .Filter.ByExcluding(evt => 
        evt.Exception is BusinessException && evt.Level == LogEventLevel.Warning)
    .WriteTo.File("logs/app-.log")
    .CreateLogger();
```

## 七、建立异常日志的使用规范与审计机制

1. **明确异常日志准入标准**

   - 什么级别的错误需要打异常日志？
   - 哪些场景必须带堆栈？哪些只需要消息？
   - 不同类型异常的保留周期是多久？

2. **代码审查卡点**

   Code Review 时重点检查：

   - 是否用异常控制业务流程？
   - 是否存在 catch 全吞异常只打日志？
   - 是否存在每层都打重复日志？
   - 预期内的失败是否用了返回值而非异常？

3. **定期日志治理**

   定期统计日志中异常的类型、数量，对高频出现的异常做专项优化：

   - 高频业务异常 → 改为返回值模式；
   - 高频系统异常 → 修复对应 bug；
   - 重复异常 → 增加聚合去重。

------

## 八、工业场景专项优化建议

1. **设备通信链路**：正常重连、瞬时超时不要打异常日志，重试超过阈值再告警；通信原始报文错误单独做开关，排查问题时才开启。
2. **数据采集链路**：数据校验失败、数值超限用状态标记，不抛异常；只有采集驱动本身崩溃才打系统异常。
3. **批量处理场景**：几万条数据批量处理时，不要每条失败都抛异常，用失败计数 + 汇总报告，最后输出一条总结日志。
4. **UI 交互场景**：用户输入错误、操作不合法用前端提示，不要抛异常打日志，避免用户误操作刷爆日志。

------

## 总结

避免异常日志滥用的核心逻辑可以概括为三句话：

1. **能不用异常就不用**：预期内的失败用返回值 / 状态机，从根源减少异常产生；
2. **非必要不打堆栈**：业务异常只记消息，系统错误才打完整堆栈；
3. **高频异常必聚合**：重复出现的异常做去重汇总，不刷屏、不浪费性能。

合理的异常日志应该是「少而精」的 —— 平时日志里很少看到异常，一旦出现就是真正需要关注和排查的问题，既不影响软件运行性能，又能高效定位故障。
