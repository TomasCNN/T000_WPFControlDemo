# 999999009-37_PLC 实时控制场景 Log4Net 故障排查完整指南

PLC 实时控制场景故障排查的核心痛点是**偶发故障难复现、停机成本高、故障点分散（通信 / IO / 运动 / 逻辑多层耦合）**。Log4Net 的核心价值是无需停机复现，通过标准化的日志埋点与分级归档，快速还原故障现场、定位根因，最大限度缩短产线停机时间。

以下内容完全贴合工控真实工况，从排查前置准备、常见故障排查思路、标准化流程、Log4Net 专属技巧、实战案例五个维度展开，可直接落地到存量 .NET Framework PLC 项目。

## 一、排查前置基础：先把日志体系搭对

故障排查的前提是日志「够全、够准、够稳」，如果日志本身缺信息、干扰多、甚至因为日志加重故障，排查就无从谈起。PLC 场景必须先落地以下 5 项基础配置，才能支撑高效排查。

### 1. 错误日志独立归档（排查效率提升 10 倍）

这是第一优先级配置：所有 `ERROR/FATAL` 级日志单独输出到专属错误日志文件，排查故障时**第一步直接打开错误文件**，不用在百万行轮询运行日志里大海捞针。

- 实现方式：通过 `LevelRangeFilter` 过滤级别，单独绑定一个 `RollingFileAppender`；
- 保留周期：错误日志保留 90 天以上，长于普通运行日志，便于追溯历史故障。

### 2. 强制携带排查关键字段

每条 PLC 相关日志必须携带核心定位字段，否则只打印「写入失败」等于白打，根本无法定位根因。

- 必带字段：寄存器地址、从站号、写入 / 读取值、错误码、重试次数、线程 ID；
- 业务上下文：工位号、批次号、当前模式（自动 / 手动），通过 `LogicalThreadContext.Properties` 全局注入，无需每条手动拼接。

### 3. 分级埋点规范（信噪比可控）

严格按严重程度分级，既保证关键信息不丢，又避免普通轮询日志刷屏淹没告警。

| 场景                         | 日志级别 | 触发条件                   |
| :--------------------------- | :------- | :------------------------- |
| 单次正常寄存器读写           | DEBUG    | 生产默认关闭，排障临时开启 |
| 单次读写失败、重试成功       | WARN     | 生产开启，预警潜在风险     |
| 连续 3 次失败、通信断开      | ERROR    | 强制开启，故障核心标识     |
| 控制异常、急停触发、程序崩溃 | FATAL    | 强制开启，致命故障留痕     |

### 4. 异步写入 + 配置热重载

- 异步写入：使用 `Log4Net.Async` 包的 `AsyncForwardingAppender`，排查时开启 Debug 也不会阻塞 PLC 控制线程，不会加重故障、影响生产；
- 热重载：初始化调用 `XmlConfigurator.ConfigureAndWatch()`，修改日志级别无需重启程序，不停产即可抓取调试信息。

### 5. 崩溃强制刷盘兜底

程序异常退出时，调用 `LogManager.Shutdown()` 强制把异步队列日志全部落盘，保留最后一刻的故障现场，避免「程序崩了、日志没了」的尴尬。

## 二、PLC 五类常见故障的日志排查思路

### 1. 通信类故障（最常见：连接中断、读写超时、从站无响应）

#### 典型现象

设备动作无响应、数据不刷新、界面提示通信异常，偶发或持续出现。

#### 排查步骤

1. **打开错误日志，定位首次失败点**

   搜索关键词：`写入失败`、`读取超时`、`通信断开`、`错误码`，找到第一次出现异常的时间点和错误码。

   - 错误码 `0x07`：寄存器地址非法，大概率是参数配置错误、地址越界；
   - 错误码 `0x0B`：从站设备忙 / 无响应，大概率是 PLC 负载高、网线接触不良、从站掉电；
   - 错误码 `SocketException`：网络层故障，检查 IP、端口、网线、交换机。

2. **回溯运行日志，看故障演进过程**

   按时间点往前翻，看失败前有没有 `WARN`级的单次失败、重试记录，是突然断开还是延迟逐渐升高后断开：

   - 突然断开：大概率是硬件触发（网线掉了、PLC 断电）；
   - 延迟逐步升高后失败：大概率是拥塞、PLC 负载过高、轮询任务过多。

3. **按需开启 Debug 抓完整报文**

   

   如果错误码不足以定位，临时开启 PLC 通信模块的 DEBUG 级别，打印完整的请求报文、响应报文、往返耗时，进一步区分是「发不出去」还是「发了没回」。

#### Log4Net 操作：临时开模块级 Debug

xaml:

```xaml
<!-- 排障时添加，保存后自动生效，无需重启 -->
<logger name="PLC通信">
  <level value="DEBUG" />
</logger>
```

### 2. 控制动作异常（走位偏差、动作不执行、流程跳步）

#### 典型现象

气缸不动作、伺服走位偏差、生产流程跳步、输出信号与预期不符。

#### 排查步骤

1. **先确认指令有没有正常下发**

   搜索寄存器地址 + 写入动作，看指令下发的时间、写入的值是否符合预期：

   - 没找到下发记录：是上位机逻辑没走到，属于软件 bug；
   - 有下发记录：继续查 PLC 侧反馈。

2. **再查反馈信号有没有正常返回**

   看对应输入寄存器的读取记录，对比指令下发时间和反馈返回时间：

   - 下发了但一直没反馈：PLC 没执行、执行失败、IO 信号故障；
   - 反馈有但逻辑判断错：上位机逻辑判断条件错误。

3. **串联时序还原完整动作链**

   按时间轴把「指令下发→PLC 响应→动作完成反馈」串起来，看哪一环断了，结合批次、工位上下文确认是偶发还是必现。

### 3. 周期抖动 / 性能类故障（扫描超时、卡顿、响应慢）

#### 典型现象

控制周期不稳定、界面卡顿、指令下发延迟大、偶尔出现周期超时告警。

#### 排查步骤

1. **定位耗时异常的周期**

   在周期首尾埋点打印耗时，搜索超过阈值的 WARN 记录，看异常周期集中在什么时段、有没有规律。

2. **排查同期高耗时操作**

   看异常时间点有没有同时执行大开销操作：

   - 大批量数据读写、数据库查询、日志同步写入；
   - UI 线程阻塞、垃圾回收（GC）触发。

3. **验证日志本身是否为干扰源**

   检查是否开启了大量 DEBUG 日志、是否用了同步写入、是否用了 `%location`等高开销反射字段，这些都会占用 CPU 加剧周期抖动。

### 4. 程序崩溃 / 异常停机类

#### 典型现象

控制程序直接退出、触发紧急停机、无响应。

#### 排查步骤

1. **第一时间打开错误日志末尾**

   找 `FATAL` 级全局未捕获异常记录，看异常类型和完整堆栈：

   - `NullReferenceException`：空对象引用，大概率是通信断开后未做空判断；
   - `OutOfMemoryException`：内存泄漏，检查是否有资源未释放、大对象持续创建；
   - `IOException`：文件 / 磁盘故障，检查日志盘是否写满、配置文件是否损坏。

2. **回溯崩溃前最后操作**

   按时间往前看运行日志，崩溃前最后执行了什么操作、切换了什么模式、下发了什么指令，还原触发条件。

3. **确认日志是否完整落盘**

   如果错误日志里没有崩溃记录，大概率是没做崩溃刷盘兜底，导致异步队列日志丢失，属于日志体系本身的缺陷，需要补充 `LogManager.Shutdown()`逻辑。

### 5. 参数 / 操作类故障（参数异常、误操作、模式切换异常）

#### 典型现象

换批次后生产不良、参数不对、手动操作后设备异常。

#### 排查步骤

1. **查操作审计日志**

   搜索参数修改、模式切换记录，看什么时间、哪个操作员、修改了哪个参数、新旧值分别是多少，快速确认是否人为误操作。

2. **查参数下发记录**

   看参数写入到 PLC 寄存器的记录，确认是参数值错了，还是下发失败了，还是 PLC 没生效。

3. **关联批次上下文**

   通过批次号串联该批次所有的参数配置、检测结果、异常记录，完整追溯批次全生命周期。

## 三、标准化故障排查五步法（现场可直接套用）

### 第一步：优先查错误日志，锁定异常点

直接打开 `error-yyyyMMdd.log` 错误专属文件，从后往前翻，找到目标故障的 ERROR/FATAL 记录，获取：异常时间、异常模块、错误码、完整堆栈。

> 80% 的 PLC 故障，靠错误日志里的堆栈和错误码就能直接定位根因。

### 第二步：按时间轴串联运行日志，还原故障时序

打开对应时间的运行日志，以故障时间点为中心，前后扩展 1~2 分钟，按时间顺序梳理：

- 故障前发生了什么（模式切换、批次切换、指令下发）；
- 故障时的状态变化（重试次数、错误码演进）；
- 故障后的处理动作（重连、复位、停机）。

### 第三步：结合业务上下文，锁定触发条件

通过工位号、批次号、产品型号等上下文字段，判断故障是否和特定批次、特定产品、特定操作相关，缩小排查范围：

- 只有某个批次出问题：大概率是参数配置问题；
- 固定时段出问题：大概率是环境干扰、负载高峰。

### 第四步：按需开启模块级 Debug，精准抓取细节

如果信息不足，**不要全局开 Debug**，只给出问题的模块开启 DEBUG 级别，保存配置后自动生效，不停机、不影响生产，抓取到足够信息后立刻改回 INFO。

### 第五步：交叉验证，确认根因

定位到疑似原因后，通过日志反向验证：

- 比如怀疑是地址错误，查所有相同地址的读写记录，看是否都失败；
- 比如怀疑是网络波动，查同一时段其他工位的通信日志，看是否同步异常。

## 四、Log4Net 专属排查技巧

### 1. 不停机动态调级别（量产线核心技巧）

依靠 `ConfigureAndWatch` 热重载能力，现场排障无需重启 PLC 程序，不中断生产：

1. 打开部署目录下的 `log4net.config`；
2. 新增 / 修改对应模块的 logger 级别（INFO→DEBUG）；
3. 保存文件，等待 3~5 秒自动生效；
4. 抓取到足够日志后，改回 INFO 级别保存即可。

### 2. 用过滤器快速筛选日志

大日志文件不要手动翻，配合 Log4Net 过滤器或日志分析工具快速定位：

- 按模块筛选：只看 `PLC通信` 日志器的记录，排除视觉、MES 等无关日志；
- 按级别筛选：只看 WARN 及以上，跳过普通轮询记录；
- 工具推荐：Notepad++ 关键词高亮、Log Parser Lizard 结构化查询、Excel 导入筛选。

### 3. 上下文全链路串联

通过 `LogicalThreadContext` 注入的 `BatchNo`、`StationNo`，可以把「参数下发→PLC 读写→IO 反馈→结果上报」整条链路的日志全部串联起来，完整还原单个产品、单个动作的全流程，不用在零散日志里拼凑。

### 4. 崩溃现场兜底保留

在全局未捕获异常事件中，先打 FATAL 日志，再调用 `LogManager.Shutdown()` 强制刷盘，最后再退出程序：

csharp:

```c#
AppDomain.CurrentDomain.UnhandledException += (sender, e) =>
{
    var ex = e.ExceptionObject as Exception;
    ILog fatalLog = LogManager.GetLogger("PLC控制");
    fatalLog.Fatal("程序触发全局未捕获异常，紧急停机", ex);
    LogManager.Shutdown(); // 强制落盘所有异步日志
};
```

这一步能保证哪怕程序直接崩掉，最后一刻的故障日志也不会丢失。

## 五、实战案例：PLC 偶发通信超时排查全流程

### 故障现象

某装配工位 PLC 偶尔出现写寄存器连续失败，一天出现 2~3 次，触发告警后自动重连恢复，无法稳定复现，现场不能长时间停机调试。

### 排查过程

1. **第一步：查错误日志**

   打开错误日志，找到失败记录：

   plaintext:

   ```tex
   2026-06-23 14:25:30.125 | ERROR | PLC通信 | 地址D200连续写入失败3次，写入值1250，错误码0x0B
      System.IO.IOException: 从站设备无响应，超时时间500ms
         在 PlcService.WriteRegister(String address, Int16 value) 位置 PlcService.cs:第156行
   ```

   初步判断：从站无响应，不是地址错误，也不是软件逻辑问题。

2. **第二步：回溯运行日志，看故障演进**

   翻 14:20~14:25 的运行日志，发现：

   - 故障前 3 分钟开始，陆续出现单次写入失败的 WARN 记录，重试后成功；
   - 写入耗时从 20ms 逐步升高到 400ms，最终超时；
   - 故障时段正好是批次切换，同时在大批量读取工艺参数。

3. **第三步：定位触发条件**

   所有故障都发生在批次切换、批量读参数的时段，判断是轮询任务叠加，通信拥塞导致超时。

4. **第四步：开 Debug 验证**

   临时开启 PLC 模块 DEBUG，等待下一次批次切换，抓取到完整的通信队列长度、请求耗时，确认是轮询任务并发过高，请求排队超时。

5. **根因与解决**

   根因：批次切换时参数读取任务和常规轮询任务叠加，通信队列拥塞。

   解决方案：优化任务优先级，常规轮询让步于参数读取，调整超时重试策略，故障彻底消失。

## 六、常见排查误区避坑

1. ❌ **只看异常消息，不看完整堆栈**

   只看到「写入失败」，不知道哪层代码出的问题、底层错误码是什么，等于白查；Error 级日志必须传完整 Exception 对象。

2. ❌ **日志不带关键参数**

   只打印「读写失败」，不写地址、错误码、重试次数，根本无法定位是哪个寄存器、什么原因失败。

3. ❌ **上来就全局开 Debug**

   全局开启 Debug 会产生海量无关日志，既难找重点，又可能影响控制性能，必须只开出问题的模块。

4. ❌ **故障后直接重启程序**

   重启后故障现场消失，日志、内存状态全部重置，再也无法复现定位，正确做法是先导出日志备份，再重启。

5. ❌ **同步日志排查故障**

   同步写 Debug 日志会阻塞控制线程，排查故障反而加重问题，甚至引发更严重的控制异常，必须用异步写入。

------

## 总结

PLC 实时控制场景用 Log4Net 排查故障，核心逻辑是：

**预埋规范的分级日志 + 错误独立归档打底 → 从错误日志快速定点 → 用运行日志还原时序 → 不停机开 Debug 抓细节 → 交叉验证确认根因**。

整套方法不用依赖专业调试工具、不用长时间停机复现，完全适配量产线不能随意停线的要求，是工控现场最高效的故障定位手段。
