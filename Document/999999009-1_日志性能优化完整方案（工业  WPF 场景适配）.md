# 999999009-1_日志性能优化完整方案（工业 / WPF 场景适配）

优化核心原则：**先减总量，再改写入，最后调细节**，优先用最低成本的手段获得最大收益。结合工业上位机、WPF 界面、高频设备采集等典型场景，以下是可直接落地的分层优化方案。

------

## 一、第一层：控制日志输出总量（收益最高、成本最低）

日志性能问题 80% 源于「输出太多、太频繁」。从源头减少日志量，是性价比最高的优化手段。

### 1. 严格分级，生产环境关闭低级别日志

#### 核心做法

- 遵循标准日志级别：`Error` > `Warning` > `Info` > `Debug` > `Trace`，级别越低信息量越大、性能开销越高。
- **生产环境默认只开启 Info 及以上级别**，`Debug`/`Trace` 级日志通过配置文件开关，排查问题时临时开启，用完立即关闭。
- 高频采集链路（如 1ms PLC 数据采集、图像帧处理）只保留 `Error` 和关键状态变更日志，连 `Info` 都要严格控制。

#### 工业场景最佳实践

- 正常运行的设备通信：只在连接 / 断开、报错时打日志，稳态通信不打日志。
- 数据采集：只在数值超阈值、状态切换时打日志，不要每个采集周期都输出。
- 支持配置热更新：无需重启程序即可动态调整日志级别，方便现场排查问题。

#### 代码示例（Serilog 级别配置）

csharp：

```c#
// 生产环境：仅输出 Info 及以上
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information() 
    // 单独给高频采集模块提高级别，只输出错误
    .MinimumLevel.Override("PlcDataCollection", Serilog.Events.LogEventLevel.Error)
    .WriteTo.File("logs/app-.log", rollingInterval: RollingInterval.Day)
    .CreateLogger();
```

### 2. 高频场景：采样输出 + 状态变更触发

针对 1ms 级别的高速采集、循环处理场景，绝对禁止逐次打日志，采用两种策略降频：

1. **采样输出**：固定时间 / 固定数量输出一次，比如每秒采样 1 次日志，而不是 1000 次 / 秒全打。
2. **状态变更输出**：只有数值变化超过阈值、设备状态切换时才打日志，稳态运行不输出。

#### 代码示例：采样日志实现

csharp:

```c#
private int _logCounter = 0;
private const int LogSampleInterval = 100; // 每采集100次打一次日志

void PlcDataReceived(double temperature)
{
    // 业务处理...
    
    // 采样输出：每100次打1次，避免高频IO
    if (Interlocked.Increment(ref _logCounter) >= LogSampleInterval)
    {
        _logCounter = 0;
        Log.Information("采集温度: {Temp}℃", temperature);
    }
    
    // 状态变更：超阈值才打告警
    if (temperature > _lastAlarmTemp + 5 || temperature < _lastAlarmTemp - 5)
    {
        Log.Warning("温度超限告警: {Temp}℃", temperature);
        _lastAlarmTemp = temperature;
    }
}
```

### 3. 彻底清理冗余日志

- 删除调试阶段的临时日志、循环内的无意义调试输出，上线前全面排查 `Debug.WriteLine`、`Console.WriteLine`。
- **生产环境必须禁用控制台输出和调试输出**：控制台渲染、VS 调试窗口输出的性能开销是文件写入的数倍到数十倍，是开发环境正常、生产环境卡顿的常见隐形原因。

## 二、第二层：写入架构优化（解决阻塞卡顿核心问题）

日志本质是 IO 操作，错误的写入方式会直接阻塞业务线程和 UI 线程，造成界面卡顿、设备通信延迟。

### 1. 全链路异步化：绝对不阻塞业务 / UI 线程

#### 核心问题

同步写日志时，调用线程会一直阻塞到磁盘写入完成才返回。

- WPF UI 线程同步写日志 → 界面卡顿、拖动无响应、控件刷新延迟；
- 设备通信线程同步写日志 → 通信帧丢失、指令响应变慢、采集丢包。

#### 解决方案

采用「**内存队列 + 后台线程批量落盘**」的异步架构：

- 业务线程调用日志方法时，只是把日志写入内存队列，立即返回，完全不阻塞；
- 单独的后台线程从队列中消费日志，批量写入磁盘 / 网络。

#### WPF 红线

UI 线程中永远不要执行同步日志写入，所有日志框架必须启用异步写入模式。

#### 代码示例（Serilog 异步配置）

csharp:

```c#
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    // 启用异步写入：后台线程批量落盘，不阻塞调用线程
    .WriteTo.Async(a => 
    {
        a.File("logs/app-.log", 
              rollingInterval: RollingInterval.Day,
              bufferSize: 1024 * 1024, // 1MB 缓冲区
              flushToDiskInterval: TimeSpan.FromSeconds(1)); // 1秒刷盘一次
    })
    .CreateLogger();
```

### 2. 写入目标优先级：本地文件 > 本地数据库 > 远端网络

#### 禁止做法

- 每条日志直接写入数据库：单次数据库插入包含事务、磁盘 IO，开销是文件写入的几十倍；
- 每条日志实时调用 HTTP 接口上传到 MES / 运维平台：网络延迟直接叠加到业务线程，网络波动会造成业务长时间阻塞。

#### 正确方案

1. 优先写入**本地文件**：性能最高、最可靠，是工业场景的首选；
2. 需要集中管理的日志，采用「**本地写文件 + 后台线程批量同步**」的方案，定期把日志文件上传到服务器，绝不实时同步；
3. 数据库日志仅保留关键审计日志，且采用批量写入，绝不逐条插入。

### 3. 批量刷盘，禁用强制立即刷盘

#### 原理

主流日志框架默认使用内存缓冲：日志先写到内存缓冲区，攒满一批再统一落盘，大幅减少磁盘 IO 次数。

- 错误配置：开启 `ImmediateFlush`（立即刷盘），要求每条日志必须立刻落到磁盘，IO 次数暴涨几十倍，写入性能暴跌。
- 正确配置：使用默认缓冲刷盘，按固定时间（如 1 秒）或缓冲区大小刷盘。

> 注意：只有安全等级极高的系统（如军工、医疗）才需要立即刷盘，常规工业场景完全没必要为了极端情况下的几条日志损失整体性能。

## 三、第三层：优化日志内容（降低 CPU 与 GC 压力）

日志内容的生成过程会消耗 CPU、产生大量临时对象，触发频繁 GC，是工业高频场景的隐形性能杀手。

### 1. 避免大对象序列化与全量 dump

#### 禁止做法

- 把完整 `DataTable`、PLC 全参数集合、批次对象、图像数据转成 JSON/XML 写入日志；
- 异常时把整个业务对象全量序列化输出。

#### 正确做法

- 只记录**关键字段**：ID、时间戳、状态码、错误码、关键数值，足够定位问题即可；
- 全量数据排查：单独做「导出诊断包」功能，需要时手动触发，不要写进常规日志。

### 2. 用结构化日志代替字符串拼接

#### 问题

大量字符串拼接（`+`、`String.Format`）会产生大量临时字符串，增加 GC 压力，高频场景下频繁 GC 会直接造成程序卡顿。

#### 方案

使用日志框架的**消息模板（结构化日志）**，框架内部做了优化，减少临时对象分配，同时支持后续结构化查询。

csharp:

```c#
// ❌ 不好：字符串拼接，产生大量临时对象
Log.Information("设备" + deviceId + "温度：" + temp + "℃，时间：" + DateTime.Now);

// ✅ 好：结构化日志，性能更优，可查询
Log.Information("设备 {DeviceId} 温度: {Temp}℃", deviceId, temp);
```

### 3. 控制异常日志的性能损耗

异常的捕获、堆栈解析、格式化开销是普通 Info 日志的几十到上百倍，高频异常会快速占满 CPU。

- **禁止用异常做正常流程控制**：比如数据校验失败、通信超时不要用抛异常 + 打日志的方式处理，用返回码 + 普通日志即可。
- **高频异常聚合输出**：同一类重复异常不要逐条打堆栈，统计次数后每分钟输出一次汇总，避免日志刷屏和 CPU 占用过高。

### 4. 延迟求值：避免提前计算日志内容

低级别日志即使最终不输出，也可能因为提前计算了日志内容（如序列化对象、拼接字符串）产生开销。

- 利用框架的条件输出特性，只有级别满足时才执行格式化；
- 复杂日志内容用 `Log.IsDebugEnabled` 先判断，再生成内容。

csharp:

```c#
if (Log.IsDebugEnabled)
{
    // 只有Debug级别开启时，才执行耗时的序列化
    var detail = JsonSerializer.Serialize(largeObject);
    Log.Debug("详细数据: {Detail}", detail);
}
```

## 四、第四层：框架与 IO 细节优化

### 1. 日志滚动与文件拆分

- 按天 / 按大小拆分日志文件，单个文件不要超过 100MB；
- 大文件写入时磁盘寻址变慢，还会导致内存映射、缓存效率下降，长期运行会让写入速度越来越慢。

### 2. 多线程并发优化

工业软件通常有大量线程（采集、通信、UI、业务处理）同时写日志，容易产生锁竞争。

- 优先用**异步队列方案**：所有线程都写入同一个内存队列，单后台线程负责写入文件，天然规避锁竞争；
- 避免多线程直接同步写文件：日志框架内部的互斥锁会造成大量线程排队阻塞，极端情况下写日志比执行业务还慢。

### 3. 内存队列限流与降级策略

给异步日志队列设置最大长度，极端情况（如程序报错疯狂输出异常）下保护主业务：

- 队列满了之后，优先丢弃 `Debug`/`Info` 级日志，保留 `Error`/`Warning`；
- 核心原则：**日志永远不能拖垮主业务**，宁可丢部分非关键日志，也不能让业务卡顿、设备失控。

## 五、工业 / WPF 场景专项优化

### 1. WPF UI 线程零阻塞

- 界面上的日志展示控件（如运行日志窗口），不要实时追加每条日志，采用「定时批量刷新」：日志先存在队列里，每隔 200ms 批量更新到 UI，减少界面渲染次数。
- 绝对不要在 `Dispatcher.Invoke` 中执行日志写入操作，避免阻塞 UI 线程。

### 2. 设备通信链路优化

- 正常通信只打心跳、状态变更日志，原始报文日志单独做开关，排查问题时才开启；
- 通信错误不要每条报文都打完整堆栈，记录错误码、时间、帧号即可，详细报文单独导出。

### 3. 批量数据处理场景

- 批量处理几万条生产记录、批次数据时，不要每条都打日志，处理完成输出一条汇总即可；
- 进度日志按百分比输出（每 10% 一条），不要每条数据都打进度。

## 六、优化优先级总结

| 优先级    | 优化手段                                       | 性能收益 | 实施成本 |
| :-------- | :--------------------------------------------- | :------- | :------- |
| 1（最高） | 生产环境关闭 Debug/Trace 日志 + 高频场景降采样 | 80%      | 极低     |
| 2         | 改为异步写入，不阻塞业务 / UI 线程             | 15%      | 低       |
| 3         | 去掉大对象序列化，改用结构化日志               | 3%       | 中       |
| 4         | 优化刷盘频率、日志滚动等参数                   | 2%       | 低       |

正常情况下，完成前两项优化就可以解决 95% 以上的日志性能问题。工业软件的日志优化核心是「平衡可靠性与性能」，在满足排障、审计需求的前提下，尽可能降低对业务运行的影响。
