**版本**：V1.1

**适用范围**：工业视觉检测、自动化设备、PLC 上位机项目

**生效日期**：2026-05-23

**维护团队**：设备软件开发组

## 一、总则

### 1.1 规范目的

- 统一团队代码风格，提高代码可读性和可维护性
- 确保项目结构清晰，新人上手时间缩短至 1 天以内
- 实现硬件可插拔，换相机 / PLC 品牌时上层代码零改动
- 避免代码变成 "屎山"，保证项目 5~10 年的生命周期
- 降低团队协作成本，减少代码冲突和沟通成本

### 1.2 核心设计原则

> **分层架构原则**：按职责分层，数字越小层级越低越稳定，上层只能依赖下层
>
> 
>
> **依赖倒置原则**：依赖抽象而非具体实现，所有硬件操作都通过接口进行
>
> 
>
> **单一职责原则**：每个文件夹、每个文件、每个类只做一件事
>
> 
>
> **清晰性优先原则**：命名要能准确反映职责，宁长勿短

## 四、代码命名规范

### 4.1 通用规则

- 类、接口、方法、属性、事件使用帕斯卡命名法
- 私有字段使用驼峰命名法（camelCase），前缀下划线
- 常量使用全大写，下划线分隔
- 布尔值必须使用 is/has/can 前缀

### 4.2 详细规则

| 类型     | 规范                              | 正确示例                               | 错误示例                          |
| :------- | :-------------------------------- | :------------------------------------- | :-------------------------------- |
| 类       | 帕斯卡命名法，名词或名词短语      | `CameraService`、`DetectionProcess`    | `cameraService`、`process`        |
| 接口     | 前缀 I + 帕斯卡命名法             | `ICamera`、`IPlc`                      | `Camera`、`CameraInterface`       |
| 方法     | 帕斯卡命名法，动词或动词短语      | `GetBitmap()`、`WaitForStartTrigger()` | `getBitmap()`、`trigger()`        |
| 属性     | 帕斯卡命名法，名词或名词短语      | `ExposureTimeUs`、`IsRunning`          | `exposureTime`、`running`         |
| 事件     | 帕斯卡命名法，动词 + 过去分词后缀 | `DefectDetected`、`ProcessCompleted`   | `DetectDefect`、`CompleteProcess` |
| 私有字段 | 下划线前缀 + 驼峰命名法           | `_camera`、`_plcService`               | `camera`、`m_plc`                 |
| 常量     | 全大写，下划线分隔                | `MAX_TIMEOUT`、`DEFAULT_EXPOSURE`      | `MaxTimeout`、`defaultExposure`   |
| 布尔值   | is/has/can 前缀 + 帕斯卡命名法    | `IsRunning`、`HasDefect`、`CanStart`   | `Running`、`Defect`、`Start`      |

### 4.3 工业场景特殊命名规范（必须遵守）

1. **硬件相关命名必须带品牌前缀**

   

   csharp:

   ```c#
   // 正确
   public class IkCamera : ICamera { }
   public class SiemensPlc : IPlc { }
   
   // 错误
   public class Camera : ICamera { }
   public class Plc : IPlc { }
   ```

   

2. **PLC 地址绝对不能用魔法字符串，必须定义常量集中管理**

   

   csharp

   ```c#
   // 正确
   public static class PlcAddressConstants
   {
       public const string START_TRIGGER = "M100";
       public const string END_TRIGGER = "D200";
       public const string ALARM = "M200";
       public const string BARCODE = "DB1.DBW0";
   }
   
   // 调用
   _plc.WriteShort(PlcAddressConstants.END_TRIGGER, 3);
   
   // 错误
   _plc.WriteShort("D200", 3);
   ```

   

3. **事件命名必须用过去分词，表示已发生的事件**

   

   csharp:

   ```c#
   // 正确
   public class DefectDetectedEvent : PubSubEvent<List<Defect>> { }
   public class ProcessCompletedEvent : PubSubEvent<bool> { }
   
   // 错误
   public class DetectDefectEvent : PubSubEvent<List<Defect>> { }
   public class CompleteProcessEvent : PubSubEvent<bool> { }
   ```

   

4. **时间单位必须在变量名中明确说明**

   

   csharp:

   ```c#
   // 正确
   public int ExposureTimeUs { get; set; } // 微秒
   public int TimeoutMs { get; set; }     // 毫秒
   public int LineSpeedMpm { get; set; }  // 米/分钟
   
   // 错误
   public int ExposureTime { get; set; }  // 不知道单位是微秒还是毫秒
   ```

   

## 五、异常处理规范（工业软件核心）

### 5.1 异常处理分层原则

> **底层抛出具体异常，中层包装通用异常，上层处理用户可见异常**
>
> 绝对不允许吞掉异常不处理，也不允许在底层弹出 MessageBox

| 层级            | 异常处理方式                                                 | 示例 |
| :-------------- | :----------------------------------------------------------- | :--- |
| **硬件抽象层**  | 捕获 SDK 原生异常，包装成统一的`HardwareException`抛出，添加详细错误信息 |      |
| **服务层**      | 捕获硬件异常，包装成`ServiceException`，记录完整日志         |      |
| **ViewModel层** | 捕获所有异常，显示用户友好的提示，不允许崩溃                 |      |
| **业务逻辑层**  | 捕获服务异常，执行补偿逻辑（复位PLC、停止设备），更新设备状态 |      |
|                 |                                                              |      |

// 正确：捕获 SDK 原生异常，包装成统一的`HardwareException`抛出，添加详细错误信息

```c#
public Bitmap GetBitmap(int timeoutMs)
{

    {
        return IK_SDK_GetImage();
    } 
    catch (IkSdkException ex)
    {
        throw new HardwareException($"相机取图失败，错误码：{ex.ErrorCode}", "Camera",ex.ErrorCode.ToString(),ex);
    }
}
```

//正确：捕获硬件异常，包装成`ServiceException`，记录完整日志 

```c#
public Bitmap GetBitmap()

    try
    {
        return _camera.GetBitmap(3000);
    }
    catch (HardwareException ex)
    {
        _logger.Error($"相机服务异常：{ex.Message}", ex);
        throw new ServiceException($"相机取图失败：{ex.Message}", ex);
    }
}
```

//正确：捕获所有异常，显示用户友好的提示，不允许崩溃 

```c#
public async Task<bool> RunAsync()

    try
    {
        // 检测流程
    }
```

//正确：捕获服务异常，执行补偿逻辑（复位PLC、停止设备），更新设备状态

### 5.2 工业场景标准异常类型

```csharp
/// <summary>
/// 硬件异常基类
/// </summary>
public class HardwareException : Exception
{
    public string HardwareType { get; }
    public string ErrorCode { get; }

    public HardwareException(string message, string hardwareType, string errorCode, Exception innerException)
        : base(message, innerException)
    {
        HardwareType = hardwareType;
        ErrorCode = errorCode;
    }
}

/// <summary>
/// 服务异常基类
/// </summary>
public class ServiceException : Exception
{
    public ServiceException(string message, Exception innerException)
        : base(message, innerException)
    {
    }
}

/// <summary>
/// 业务异常基类
/// </summary>
public class BusinessException : Exception
{
    public BusinessException(string message)
        : base(message)
    {
    }
}
```

### 5.3 绝对禁止的异常处理行为

1. ❌ **吞掉异常不处理**：`try { ... } catch { }`
2. ❌ **在底层弹出 MessageBox**：硬件层和服务层绝对不能有 UI 相关代码
3. ❌ **捕获所有异常不区分类型**：`catch (Exception ex) { ... }`（只有 ViewModel 层允许）
4. ❌ **异常信息不包含上下文**：只写 "相机错误"，不写错误码和详细信息
5. ❌ **异常时不释放资源**：发生异常时 Bitmap、文件句柄等资源没有释放

## 六、资源管理规范（解决工业软件内存泄漏）

### 6.1 非托管资源释放规范

所有包含非托管资源的类必须实现完整的 IDisposable 模式：

csharp:

```c#
public class IkCamera : ICamera
{
    private bool _disposed = false;
    private Bitmap _lineScanImage;
    private IntPtr _cameraHandle;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 释放托管资源
            _lineScanImage?.Dispose();
            _lineScanImage = null;
        }

        // 释放非托管资源
        if (_cameraHandle != IntPtr.Zero)
        {
            IK_SDK_CloseDevice(_cameraHandle);
            _cameraHandle = IntPtr.Zero;
        }

        _disposed = true;
    }

    ~IkCamera()
    {
        Dispose(false);
    }
}
```

### 6.2 Bitmap 资源管理规范（工业软件最常见内存泄漏点）

1. **谁创建谁释放**：创建 Bitmap 的代码必须负责释放它

2. **使用 using 语句**：局部变量的 Bitmap 必须用 using 包裹

   csharp:

   ```c#
   // 正确
   using (var bmp = _camera.GetBitmap())
   {
       // 处理图像
   } // 自动释放
   ```

   

3. **静态变量必须手动释放**：静态 Bitmap 在程序退出时必须释放

4. **图像克隆后释放原图**：

   csharp:

   ```c#
   // 正确
   var newBitmap = new Bitmap(_lineScanImage);
   _lineScanImage.Dispose();
   _lineScanImage = null;
   return newBitmap;
   ```

   

### 6.3 事件订阅与取消规范

所有事件订阅必须保存订阅令牌，并在对象销毁时取消：

csharp:

```c#
public class MonitorViewModel : BindableBase, IDisposable
{
    private readonly IEventAggregator _eventAggregator;
    private SubscriptionToken _defectEventToken;

    public MonitorViewModel(IEventAggregator eventAggregator)
    {
        _eventAggregator = eventAggregator;
        
        // 订阅事件并保存令牌
        _defectEventToken = _eventAggregator.GetEvent<DefectDetectedEvent>()
            .Subscribe(OnDefectDetected, ThreadOption.UIThread);
    }

    public void Dispose()
    {
        // 取消订阅，防止内存泄漏
        _defectEventToken?.Dispose();
    }
}
```

### 7.1 测试范围

| 模块                   | 是否需要测试 | 测试重点                                 |
| :--------------------- | :----------- | :--------------------------------------- |

| **05_ViewModels**      | 部分         | 测试命令和属性变更通知                   |

| **07_Models**          | 否           | 纯数据结构                               |
| **08_Data**            | ✅ 是         | 测试数据读写逻辑                         |
| **09_Common**          | ✅ 是         | 所有通用工具类                           |

### 7.2 测试命名规范

```
被测试方法名_测试场景_预期结果
```

csharp:

```

[TestMethod]
public void WaitForStartTrigger_TriggerReceivedWithinTimeout_ReturnsTrue()

[TestMethod]
```

### 7.3 测试结构规范（AAA 模式）

csharp:

```c#
[TestMethod]
public void GetBitmap_ValidTimeout_ReturnsBitmap()
{
    // Arrange：准备测试数据和模拟对象
    var mockCamera = new Mock<ICamera>();
    var mockLogger = new Mock<ILogger>();
    var expectedBitmap = new Bitmap(1920, 1080);
    
    mockCamera.Setup(c => c.GetBitmap(3000)).Returns(expectedBitmap);
    
    var cameraService = new CameraService(mockCamera.Object, mockLogger.Object);

    // Act：执行被测试方法
    var result = cameraService.GetBitmap();

    // Assert：验证结果
    Assert.IsNotNull(result);
    mockCamera.Verify(c => c.GetBitmap(3000), Times.Once);
}
```

### 7.4 工业场景测试最佳实践

1. **使用 Mock 框架模拟硬件**：用 Moq 模拟 ICamera 和 IPlc 接口，不需要连接真实硬件就能测试
2. **重点测试异常流程**：模拟硬件断开、通讯超时、数据异常等情况
3. **测试边界条件**：测试超时时间为 0、负数、最大值等情况
4. **每个测试方法只测试一个场景**：一个测试方法只验证一个行为

| test     | 添加或修改测试代码               |
| chore    | 构建过程或辅助工具的变动         |

### 8.3 分支管理规范

| 分支名        | 作用                       | 合并规则                                          |
| :------------ | :------------------------- | :------------------------------------------------ |

### 8.4 提交最佳实践

1. **每次提交只做一件事**：不要把多个不相关的修改放在同一个提交中
2. **提交信息要清晰准确**：让其他开发者看到提交信息就知道做了什么修改

## 十一、性能优化规范（工业 CT 优化核心）

### 11.1 总体原则

> **先测量再优化**：永远用性能分析工具（Visual Studio Profiler）定位瓶颈，不要凭感觉优化
>
> 
>
> **工业软件第一优先级：低延迟 > 低 CPU > 低内存**

### 11.2 UI 层性能优化（解决界面卡顿）

#### 11.2.1 强制开启 UI 虚拟化

所有显示超过 50 条数据的列表 / 表格必须开启虚拟化：

xaml:

```xaml
<!-- ✅ 正确：DataGrid完整虚拟化配置 -->
<DataGrid 
    ItemsSource="{Binding DefectList}"
    VirtualizingStackPanel.IsVirtualizing="True"
    VirtualizingStackPanel.VirtualizationMode="Recycling"
    ScrollViewer.CanContentScroll="True"
    EnableRowVirtualization="True"
    EnableColumnVirtualization="False"
    MaxHeight="600">
</DataGrid>

<!-- ❌ 错误：把DataGrid放在ScrollViewer里，虚拟化完全失效 -->
<ScrollViewer>
    <DataGrid ItemsSource="{Binding DefectList}"/>
</ScrollViewer>
```

#### 11.2.2 布局优化

- 每个模块的根容器嵌套不超过 3 层
- 线性布局优先用`StackPanel`，不要用`Grid`
- 图形绘制优先用`Canvas`，不要用多个`Border`叠加
- 避免在`Grid`中使用大量`*`号尺寸

#### 11.2.3 图像显示优化

- 大图像显示前先缩放到控件大小，不要直接显示原图
- 使用`WriteableBitmap`代替`Bitmap`进行实时图像更新
- 图像更新频率不要超过 30fps，人眼无法区分更高频率

### 11.3 数据绑定优化

#### 11.3.1 正确实现 INotifyPropertyChanged

只有属性值真正变化时才触发通知：

csharp:

```c#
// ✅ 正确
private string _statusMessage;
public string StatusMessage
{
    get => _statusMessage;
    set
    {
        if (_statusMessage != value)
        {
            _statusMessage = value;
            OnPropertyChanged();
        }
    }
}

// ❌ 错误：每次赋值都触发通知
public string StatusMessage
{
    get => _statusMessage;
    set
    {
        _statusMessage = value;
        OnPropertyChanged();
    }
}
```

#### 11.3.2 批量数据更新

大量数据更新时先挂起绑定，更新完成后再恢复：

csharp:

```c#
// ✅ 正确：批量更新
DefectList.Clear();
foreach (var defect in defects)
{
    DefectList.Add(defect);
}

// ❌ 错误：循环中逐个触发通知
foreach (var defect in defects)
{
    DefectList.Add(defect);
}
```

### 11.4 硬件交互优化（CT 优化核心）

#### 11.4.1 分级等待策略

所有硬件信号等待必须使用分级等待：

csharp:

```c#
// ✅ 正确：前100ms自旋，之后睡眠
public bool WaitForStartTrigger(int timeoutMs = 30000)
{
    var sw = Stopwatch.StartNew();
    var spinWait = new SpinWait();

    while (sw.ElapsedMilliseconds < timeoutMs)
    {
        if (_plc.ReadBool(PlcAddressConstants.START_TRIGGER))
            return true;

        if (sw.ElapsedMilliseconds < 100)
            spinWait.SpinOnce();
        else
            Thread.Sleep(5);
    }

    return false;
}

// ❌ 错误：固定Sleep(50)，延迟高达50ms
public bool WaitForStartTrigger(int timeoutMs = 30000)
{
    while (timeoutMs > 0)
    {
        if (_plc.ReadBool("M100"))
            return true;
        Thread.Sleep(50);
        timeoutMs -= 50;
    }
    return false;
}
```

#### 11.4.2 批量读写 PLC

尽量减少 PLC 通讯次数，一次读写多个地址：

csharp:

```c#
// ✅ 正确：一次读取10个地址
var values = _plc.ReadMultipleShorts("DB1.DBW0", 10);

// ❌ 错误：循环读取10次
for (int i = 0; i < 10; i++)
{
    var value = _plc.ReadShort($"DB1.DBW{i*2}");
}
```

#### 11.4.3 提前发 PLC 结束信号

拿到图像后立刻发结束信号，不要等算法处理完：

csharp:

```c#
// ✅ 正确：设备和电脑并行工作
var image = await _cameraService.GetBitmapAsync();
_plcService.SendEndTrigger(true); // 立刻发信号
var defects = await _algorithmService.DetectDefectsAsync(image);

// ❌ 错误：等算法处理完再发信号，CT增加几十到几百ms
var image = await _cameraService.GetBitmapAsync();
var defects = await _algorithmService.DetectDefectsAsync(image);
_plcService.SendEndTrigger(true);
```

### 11.5 内存管理优化

- 所有 Bitmap 使用完必须立即调用`Dispose()`
- 静态变量不要引用大对象
- 每小时执行一次强制 GC：`GC.Collect(); GC.WaitForPendingFinalizers();`
- 避免使用`ArrayList`和非泛型集合，使用泛型集合`List<T>`

## 十二、日志规范（问题排查唯一依据）

### 12.1 日志级别规范

| 级别      | 使用场景                             | 示例                                     |
| :-------- | :----------------------------------- | :--------------------------------------- |

### 12.3 日志配置规范

- 日志按日期归档，每天一个文件
- 单个日志文件大小不超过 10MB
- 保留最近 30 天的日志
- 生产环境默认启用 Info 及以上级别
- 所有异常必须记录完整的堆栈信息

### 12.4 工业场景特殊日志要求

3. **所有检测结果必须记录日志**：条码、结果、耗时、缺陷数量
4. **所有报警必须记录日志**：报警时间、报警内容、报警级别
5. **敏感信息必须脱敏**：密码、密钥、IP 地址不能记录明文

## 十三、安全规范（工业设备生命线）

### 13.1 权限管理规范

#### 13.1.1 角色权限划分

| 角色       | 权限                                        |
| :--------- | :------------------------------------------ |

#### 13.1.2 权限控制实现

- 没有权限的功能要隐藏或禁用
- 权限验证必须在服务层也做一次，不能只在 UI 层做
- 用户密码必须加密存储，不能明文保存

### 13.2 输入验证规范

所有用户输入必须进行验证，防止非法输入：

- 数值输入必须验证范围：曝光时间 1~100000μs
- 字符串输入必须验证长度和格式：条码长度 1~20 位
- 文件路径输入必须验证合法性
- 所有数据库操作必须使用参数化查询，防止 SQL 注入

csharp:

```c#
// ✅ 正确：参数化查询
public void SaveRecord(ProductRecord record)
{
    using var conn = _databaseContext.GetConnection();
    conn.Execute(@"
        INSERT INTO ProductRecords (Barcode, IsOk, DefectCount, CreateTime)
        VALUES (@Barcode, @IsOk, @DefectCount, @CreateTime)",
        record);
}

// ❌ 错误：字符串拼接，存在SQL注入风险
public void SaveRecord(ProductRecord record)
{
    using var conn = _databaseContext.GetConnection();
    conn.Execute($"INSERT INTO ProductRecords (Barcode) VALUES ('{record.Barcode}')");
}
```

### 13.3 数据安全规范

- 配置文件中的密码和密钥必须加密存储
- 数据库必须设置密码，禁止空密码
- 重要数据必须定期备份，每天自动备份
- 图像和数据文件必须设置访问权限，禁止普通用户删除
- 系统退出时必须保存所有未保存的参数和数据

### 13.4 设备控制安全规范

- 急停按钮优先级最高，任何情况下按下急停都必须立即停止设备
- 所有设备操作都要有确认提示，防止误操作
- 设备运行时禁止修改关键参数
- 异常发生时必须自动停止设备并复位所有输出
- 所有 PLC 输出必须有硬件互锁，不能只靠软件控制

### 13.5 网络安全规范

- 设备网络与办公网络物理隔离
- 禁止设备连接公网
- PLC 和相机使用静态 IP 地址
- 关闭不必要的网络服务和端口
- 定期更新操作系统和软件补丁

### 17.4 部署后验证流程

1. 检查程序是否能正常启动
2. 检查硬件是否能正常连接（相机、PLC）
3. 运行一次完整的检测流程，验证功能正常
4. 检查日志是否正常生成
5. 检查图像是否正常保存
6. 检查数据库是否正常读写
7. 测试急停按钮功能

## 十八、调试规范（工业现场安全第一）

### 18.1 调试前准备

1. 断开设备与产线的连接，确保调试过程不会影响生产
2. 备份当前所有配置和数据
3. 准备好调试工具：万用表、示波器、笔记本电脑
4. 通知现场操作人员，获得调试许可
5. 穿戴好个人防护装备

### 18.2 调试流程

1. 先在模拟模式下调试，验证软件逻辑正确
2. 再连接硬件进行单步调试
3. 逐步增加运行速度，从低速到高速
4. 连续运行 24 小时，验证系统稳定性
5. 调试完成后恢复所有配置和参数
6. 清理调试过程中产生的临时文件和日志

### 18.3 调试安全规范

1. **绝对禁止在生产环境进行调试**
2. 调试过程中必须有专人值守，随时准备按下急停
3. 禁止修改生产数据和历史记录
4. 调试完成后必须关闭调试模式
5. 所有调试操作必须记录在调试日志中

### 18.4 调试日志规范

调试日志必须包含以下信息：

- 调试时间
- 调试人员
- 调试目的
- 调试步骤
- 调试结果
- 发现的问题
- 解决方案

## 十九、故障排查规范（快速定位问题）

### 19.1 故障排查总体流程

> **先看日志，再查硬件，最后查软件**
>
> 80% 的工业设备问题都能通过日志快速定位

1. **第一步：查看日志**

   

   - 查看最近的错误日志和警告日志
   - 确定故障发生的时间和模块
   - 查找故障发生前的异常信息

   

2. **第二步：检查硬件**

   

   - 检查电源是否正常
   - 检查网线和数据线是否连接牢固
   - 检查硬件指示灯状态
   - 重启硬件设备

   

3. **第三步：检查软件**

   

   - 检查程序是否正常运行
   - 检查配置参数是否正确
   - 重启程序
   - 恢复到上一个正常的配置版本

   

4. **第四步：联系技术支持**

   

   - 提供详细的故障描述
   - 提供日志文件和配置文件
   - 提供硬件型号和软件版本

   

### 19.2 常见故障排查指南

| 故障现象       | 可能原因                                                   | 排查步骤                                                     |
| :------------- | :--------------------------------------------------------- | :----------------------------------------------------------- |
| 相机取图超时   | 1. 相机断电2. 网线松动3. 触发信号异常4. 相机 SDK 异常      | 1. 检查相机电源2. 检查网线连接3. 用万用表测量触发信号4. 重启相机和程序 |
| PLC 连接失败   | 1. PLC 断电2. IP 地址错误3. 网线松动4. 防火墙拦截          | 1. 检查 PLC 电源2. 检查 IP 地址配置3. 检查网线连接4. 关闭防火墙 |
| 界面卡顿       | 1. 图像更新频率过高2. 数据量过大3. 内存泄漏4. CPU 占用过高 | 1. 降低图像更新频率2. 开启 UI 虚拟化3. 检查内存使用情况4. 重启程序 |
| 检测结果不准确 | 1. 相机参数变化2. 光源亮度变化3. 算法参数变化4. 相机偏移   | 1. 检查相机参数2. 检查光源亮度3. 检查算法参数4. 重新校准相机 |

### 19.3 故障记录与上报

所有故障必须记录在故障管理系统中，包含以下信息：

- 故障发生时间
- 故障现象
- 故障原因
- 解决方案
- 处理人员
- 处理时间

## 二十、设备校准规范（保证检测精度）

### 20.1 校准项目与周期

| 校准项目     | 校准周期             | 负责人 |
| :----------- | :------------------- | :----- |
| 相机标定     | 每月一次或更换相机后 | 工程师 |
| 像素当量校准 | 每月一次或更换镜头后 | 工程师 |
| 光源校准     | 每周一次             | 工艺员 |
| 检测精度验证 | 每天一次             | 操作员 |

### 20.2 校准流程

#### 20.2.1 像素当量校准

1. 放置标准标定板在相机视野中心
2. 采集标定板图像
3. 运行像素当量校准程序
4. 计算像素当量值
5. 保存校准结果到配置文件
6. 验证校准精度：测量标准件尺寸，误差不超过 ±0.01mm

#### 20.2.2 光源校准

1. 放置标准白板在相机视野中心
2. 采集白板图像
3. 调整光源亮度，使图像灰度值在 128±10 之间
4. 保存光源参数到配置文件
5. 记录校准时间和参数

### 20.3 校准记录

所有校准必须记录在校准记录表中，包含以下信息：

- 校准时间
- 校准项目
- 校准前参数
- 校准后参数
- 校准结果
- 校准人员

## 二十二、版本发布规范

### 22.1 版本号规则

采用语义化版本号：`主版本号.次版本号.修订号`

- **主版本号**：不兼容的 API 修改
- **次版本号**：向下兼容的功能性新增
- **修订号**：向下兼容的问题修正

**示例**：

- V1.0.0：第一个正式版本
- V1.1.0：新增算法参数自动调整功能
- V1.1.1：修复相机取图超时的 bug

### 22.2 发布前测试流程

1. 单元测试：所有单元测试必须通过
2. 集成测试：所有模块集成测试通过
3. 系统测试：完整的系统功能测试通过
4. 压力测试：连续运行 72 小时无异常
5. 现场测试：在客户现场进行实际生产测试

### 22.3 发布流程

1. 从 develop 分支创建 release 分支
2. 在 release 分支进行发布前测试和 bug 修复
3. 测试通过后合并到 main 分支和 develop 分支
4. 在 main 分支打版本标签
5. 制作安装包
6. 发布安装包和发布说明
7. 更新文档和用户手册

### 22.4 版本回滚机制

- 每个版本都保留完整的安装包和配置文件
- 新版本发布后保留上一个版本的安装包至少 3 个月
- 出现严重问题时可以快速回滚到上一个稳定版本
- 回滚后必须记录回滚原因和时间

## 二十四、用户操作规范

### 24.1 操作人员分级操作权限

1. **操作员日常操作**

- 设备启停、急停复位、批量生产启停
- 查看实时画面、检测统计、报警信息
- 导出当日生产报表、缺陷明细
- 禁止修改工艺、系统、硬件参数

1. **工艺员操作权限**

- 包含全部操作员权限
- 调整相机曝光、增益、算法判定阈值
- 保存工艺配方、切换生产型号
- 查看历史缺陷图像与追溯数据

1. **设备工程师操作权限**

- 包含全部工艺员权限
- 硬件 IP、通讯地址、IO 点位配置
- 设备标定、偏差补偿、系统诊断
- 日志查询、数据备份、故障调试

1. **管理员操作权限**

- 全功能权限，用户账号新增 / 禁用 / 密码重置
- 系统初始化、版本升级、权限分配

### 24.2 标准开机操作流程

1. 检查设备供电、气源、线路外观无异常
2. 依次上电：工控机→光源→线扫相机→PLC 控制器
3. 等待硬件自检完成，启动上位机软件
4. 自动连接相机、PLC、数据库服务
5. 查看设备状态为空闲无报警，方可投入生产

### 24.3 标准关机操作流程

1. 停止当前生产任务，等待工位物料走完
2. 复位所有 PLC 输出信号，关闭光源
3. 正常退出上位机程序，释放硬件资源
4. 依次断电：PLC→相机→光源→工控机
5. 清理现场，记录当班生产与故障信息

### 24.4 高危操作禁令

- 运行中严禁插拔相机网线、PLC 通讯线
- 未停稳设备禁止伸手进入检测区域
- 禁止强行结束程序进程、强制断电
- 禁止私自拷贝、篡改程序与配置文件
- 报警未消除前禁止重启启动生产

### 24.5 操作记录规范

关键操作自动留存日志：账号、时间、操作行为、前后参数值；人工异常操作手写当班台账。

## 二十九、异步与多线程规范

### 29.1 线程使用准则

- UI 逻辑仅在主线程执行，禁止子线程直接操作控件
- 硬件采集、算法运算、文件读写、数据库操作全部异步子线程
- 线程职责单一，禁止跨线程混用硬件句柄、图像对象

### 29.2 async/await 统一写法

- IO 密集型：相机、PLC、文件、数据库优先异步等待
- 计算密集型：使用`Task.Run`后台调度，不阻塞界面

### 29.3 线程安全约束

- 共享全局变量读写加锁保护
- Bitmap、硬件句柄禁止多线程同时调用
- 任务取消令牌 CancellationToken 统一管控终止流程

### 29.4 禁止写法

- 主线程长时间 Sleep、死循环等待
- 无限制创建大量后台线程
- 子线程直接弹窗、修改绑定属性

## 三十四、数据库表设计规范

### 34.1 基础设计原则

1. 遵循三范式，减少数据冗余，关联表通过主键外键约束绑定
2. 表名、字段名统一采用帕斯卡命名，表意直观无歧义
3. 字段类型按需匹配，数值、文本、时间类型严格区分，避免类型溢出
4. 每张表必设主键索引，高频查询字段单独建立索引，提升检索效率

### 34.2 通用基础字段

所有业务数据表统一标配基础字段

- Id：自增主键编号
- CreateTime：数据生成时间
- UpdateTime：数据最后修改时间
- IsDeleted：逻辑删除标记，禁止物理删除业务数据
- Operator：操作人账号

### 34.3 核心业务表结构标准

1. **产品基础表 ProductInfo**：产品编码、产品名称、规格型号、默认工艺参数编号
2. **生产记录表 ProductionRecord**：条码、产品 ID、检测结果、缺陷总数、采集耗时、工位编号
3. **缺陷明细表 DefectDetail**：关联生产 ID、缺陷类型、坐标位置、尺寸参数、缺陷图像路径
4. **设备运行表 DeviceRunLog**：启停时间、运行时长、故障次数、硬件状态、操作人员
5. **系统操作记录表 SysOperateLog**：账号、操作模块、操作内容、参数变更前后值、IP 地址

### 34.4 SQL 编写规范

1. 语句关键字大写，代码换行分层排版，可读性优先
2. 杜绝`select *`，按需指定查询字段
3. 批量操作使用事务包裹，保证数据原子性，失败自动回滚
4. 分页查询统一封装通用方法，适配大批量数据查询场景

### 34.5 数据库运维规范

1. 定期统计索引使用情况，清理无效冗余索引
2. 按月归档历史生产数据，拆分老旧数据分区存储
3. 严格管控数据库账号权限，区分查询、读写、管理员权限

## 三十五、MES/CIM 外协对接通讯规范

### 35.1 通讯交互方式

1. 主流采用 HTTP 接口、WCF 服务、Socket 报文三种模式，项目内统一单一通讯架构
2. 设备主动上报生产数据、报警信息；MES 下发生产任务、配方参数

### 35.2 报文数据格式

1. 统一使用 JSON 标准格式传输，字段名称双方约定固定不变
2. 报文头部携带设备编号、时间戳、校验码，防止数据篡改、丢包
3. 数值数据统一单位，字符串去除首尾空格，空值统一固定标识

### 35.3 交互流程规范

1. 握手校验：设备上线主动注册，MES 校验设备合法性后建立通讯通道
2. 任务下发：MES 推送生产工单，本地缓存任务，校验合规后启动生产
3. 数据上报：单产品检测完成立即上报结果，超时未应答自动重试 3 次
4. 离线缓存：网络中断暂存本地数据，网络恢复批量补发，不丢失生产数据

### 35.4 异常处理规范

1. 通讯超时、报文解析失败、数据校验不通过均记录详细日志
2. 连续通讯异常触发本地告警，提示工作人员排查网络与对接配置
3. 接口版本兼容适配，新旧报文格式可兼容解析，避免对接报错

------

## 三十六、跨项目复用组件规范

### 36.1 组件拆分标准

1. 通用工具类、硬件基础接口、日志框架、数据库操作封装为独立公共组件
2. 按功能拆分模块包，单一组件只负责一类通用能力，符合单一职责
3. 组件内部逻辑封闭，对外仅暴露必要调用方法，隐藏底层实现细节

### 36.2 版本管理规范

1. 公共组件独立版本管控，版本号变更记录功能迭代与问题修复
2. 项目引用固定组件版本，跨项目升级组件统一测试，规避兼容问题
3. 组件更新同步更新使用文档，标注接口变更、废弃方法说明

### 36.3 复用调用约束

1. 禁止直接修改引用的公共组件源码，自定义扩展采用继承、重载方式实现
2. 组件调用传入参数严格校验，捕获组件抛出异常，做业务层兜底处理
3. 同类功能优先调用成熟复用组件，禁止重复编写同质化代码

## 三十七、弹窗与交互提示规范

### 37.1 弹窗分级规则

1. 普通提示：操作成功、参数保存完成，轻量浮窗自动关闭
2. 确认弹窗：删除数据、启停设备、切换配方，必须手动确认操作

4. 故障弹窗：设备停机、硬件异常，处理完毕方可关闭弹窗

### 37.2 文案措辞规范

2. 错误提示区分操作人员提示、技术排查提示，分层展示信息
3. 按钮文字统一规范：确定、取消、保存、复位、查看详情、立即排查

### 37.3 弹窗行为约束

1. 高危操作弹窗默认聚焦取消按钮，防止误触确认
2. 弹窗弹出时锁定底层界面，禁止后台界面操作干扰流程

## 三十八、内存与句柄管控补充规范

### 38.1 句柄使用准则

1. 相机、PLC、文件、数据库连接句柄，遵循即用即释原则
2. 全局常驻句柄初始化统一创建，程序退出统一销毁，杜绝零散释放
3. 定时检测句柄数量，异常激增主动告警，排查泄漏点位

### 38.2 大内存对象管控

1. 大图、大批量数据集不做全局静态缓存，使用结束立刻释放引用
2. 批量数据处理采用分段读取、分段解析，避免一次性加载全部数据
3. 闲置空闲时段执行内存整理，降低程序内存常驻占用

### 38.3 内存泄漏排查标准

1. 长期运行监控内存曲线，持续稳步上涨判定存在泄漏
2. 重点排查图像对象、事件订阅、数据库连接、线程实例四类高频泄漏点
3. 修复后连续 72 小时压测，验证内存趋于平稳无异常增长
