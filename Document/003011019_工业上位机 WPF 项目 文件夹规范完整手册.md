# 003011019_工业上位机 WPF 项目 文件夹规范完整手册

完全基于你正在使用的**带数字前缀的分层架构模板**，从**作用→文件类型→命名规范**三个维度给出工业界统一标准，所有规则都经过数百台设备验证，确保团队协作顺畅、代码结构清晰、维护成本最低。

------

## 问题一：详细说明各文件夹的作用

### 核心设计原则

> **数字前缀 = 依赖层级**：数字越小，层级越低，越稳定；数字越大，层级越高，越易变。
>
> 上层只能依赖下层，下层绝对不能依赖上层。

| 文件夹                 | 层级                 | 核心作用                                           | 工业场景特殊意义                                             |
| :--------------------- | :------------------- | :------------------------------------------------- | :----------------------------------------------------------- |
| **01_Abstractions**    | 硬件抽象层（最底层） | 定义所有硬件和服务的**统一接口**，隔离变化         | 工业软件的灵魂。所有上层代码只依赖接口，不依赖具体硬件实现。换相机 / PLC 品牌时，上层代码零改动 |
| **02_Implementations** | 硬件实现层           | 不同品牌硬件的**具体实现代码**                     | 所有硬件相关的 SDK 调用、寄存器操作都放在这里。硬件变更时，只需要修改或新增这个文件夹下的代码 |
| **03_Services**        | 服务层               | 封装通用能力，提供**强类型、安全的 API**给上层调用 | 隐藏底层硬件的复杂操作，处理通用异常、重试、超时逻辑。业务层不需要关心硬件的具体细节 |
| **04_Business**        | 业务逻辑层           | 核心业务流程编排、业务规则判断、设备状态管理       | 整个系统的大脑。只做流程控制，不做任何具体实现，所有操作都委托给服务层 |
| **05_ViewModels**      | MVVM 层              | UI 逻辑、数据绑定、命令处理、UI 状态管理           | 连接 UI 和业务的桥梁。只处理 UI 相关逻辑，不包含任何业务规则和硬件操作 |
| **06_Views**           | UI 层                | 界面布局、样式、控件、用户输入处理                 | 只负责显示和用户输入，不包含任何业务逻辑。所有逻辑都通过绑定交给 ViewModel |
| **07_Models**          | 公共数据模型层       | 纯数据结构，无任何逻辑                             | 所有层都可以依赖的公共数据载体。在不同模块之间传递数据       |
| **08_Data**            | 数据访问层           | 数据库、文件、配置的读写操作                       | 统一管理所有数据持久化逻辑，上层不需要关心数据存在哪里       |
| **09_Common**          | 通用工具层           | 所有模块通用的辅助类、扩展方法、转换器             | 与业务无关的通用工具代码，可以在任何项目中复用               |
| **Configs**            | 配置层               | 所有系统配置文件                                   | 所有可配置的参数都放在这里，不需要修改代码就能调整系统行为   |

### 关键说明

- **为什么用数字前缀？**：解决方案管理器会按数字顺序自动排列，正好对应依赖方向（01→09）。任何开发者打开项目，一眼就能看出哪个是底层、哪个是上层，从根本上避免反向依赖。
- **为什么没有按功能模块分文件夹？**：工业软件的核心变化来自硬件和业务流程，按职责分层比按功能分模块更稳定、更易维护。

## 问题二：详细说明各文件夹的文件类型

### 严格的文件类型隔离原则

**每个文件夹只能放一种类型的文件**，绝对不允许混合职责。这是避免代码混乱的最有效手段。

| 文件夹                 | 允许的文件类型                             | 绝对禁止放入                             | 工业项目示例                                                 |
| :--------------------- | :----------------------------------------- | :--------------------------------------- | :----------------------------------------------------------- |
| **01_Abstractions**    | 接口文件 (.cs)                             | 任何实现类、任何业务逻辑、任何 UI 代码   | `ICamera.cs`、`IPlc.cs`、`ILogger.cs`、`IDataService.cs`     |
| **02_Implementations** | 接口的具体实现类 (.cs)                     | 任何业务逻辑、任何 UI 代码               | `IkCamera.cs`、`SiemensPlc.cs`、`NLogLogger.cs`、`SqliteDataService.cs` |
| **03_Services**        | 服务类 (.cs)                               | 任何 UI 代码、任何业务流程               | `CameraService.cs`、`PlcService.cs`、`AlgorithmService.cs`、`ConfigService.cs` |
| **04_Business**        | 流程类、状态机类、管理器类 (.cs)           | 任何硬件操作、任何 UI 代码、任何数据访问 | `DetectionProcess.cs`、`ProductionManager.cs`、`StateMachine.cs`、`AlarmManager.cs` |
| **05_ViewModels**      | ViewModel 类 (.cs)                         | 任何硬件操作、任何业务逻辑、任何数据访问 | `MainViewModel.cs`、`MonitorViewModel.cs`、`ParameterViewModel.cs`、`DataViewModel.cs` |
| **06_Views**           | XAML 文件 + 对应的.xaml.cs 代码隐藏文件    | 任何业务逻辑、任何硬件调用、任何数据处理 | `MainWindow.xaml`、`MonitorView.xaml`、`ParameterView.xaml`、`IoMonitorView.xaml` |
| **07_Models**          | 纯数据实体类、DTO 类、枚举 (.cs)           | 任何方法、任何逻辑、任何依赖             | `Defect.cs`、`ProductRecord.cs`、`AppConfig.cs`、`DeviceStatus.cs`(枚举) |
| **08_Data**            | 数据库上下文、文件管理器、数据仓储类 (.cs) | 任何业务逻辑、任何 UI 代码               | `DatabaseContext.cs`、`FileManager.cs`、`DefectRepository.cs`、`ImageSaver.cs` |
| **09_Common**          | 转换器、扩展方法、帮助类、常量类 (.cs)     | 任何业务相关代码                         | `BoolToColorConverter.cs`、`BitmapExtensions.cs`、`ImageHelper.cs`、`TimeHelper.cs` |
| **Configs**            | 配置文件 (.json、.config、.xml)            | 任何代码文件                             | `appsettings.json`、`NLog.config`、`CameraParams.json`、`PlcAddresses.json` |

### 子文件夹组织规范

当某个文件夹下的文件超过 10 个时，按功能拆分子文件夹：

plaintext

```tex
02_Implementations/
├── Cameras/                  # 所有相机实现
│   ├── IkCamera.cs
│   ├── HikCamera.cs
│   └── BaslerCamera.cs
├── Plcs/                     # 所有PLC实现
│   ├── SiemensPlc.cs
│   ├── OmronPlc.cs
│   └── MitsubishiPlc.cs
└── Loggers/                  # 所有日志实现
    └── NLogLogger.cs

06_Views/
├── MonitorView/              # 实时监控模块
│   ├── MonitorView.xaml
│   └── MonitorView.xaml.cs
├── ParameterView/            # 参数配置模块
│   ├── ParameterView.xaml
│   └── ParameterView.xaml.cs
└── IoMonitorView/            # IO监控模块
    ├── IoMonitorView.xaml
    └── IoMonitorView.xaml.cs
```

## 问题三：详细说明各文件夹的命名规范

### 核心命名原则

> **清晰性优先，简洁性其次**。命名要能准确反映文件的职责，让开发者看到名字就知道这个文件是做什么的。

### 一、文件夹命名规范

| 类型     | 规范                             | 示例                                                   |
| :------- | :------------------------------- | :----------------------------------------------------- |
| 根文件夹 | `数字_英文名称`，帕斯卡命名法    | `01_Abstractions`、`02_Implementations`、`03_Services` |
| 子文件夹 | 英文名称，帕斯卡命名法，复数形式 | `Cameras`、`Plcs`、`Converters`、`Extensions`          |

**数字前缀说明**：

- 必须是两位数字，不足两位前面补 0
- 数字间隔为 1，方便以后插入新的层级
- 数字越小，层级越低，越稳定

### 二、文件命名规范

| 文件夹             | 命名规范                                       | 示例                                                         |
| :----------------- | :--------------------------------------------- | :----------------------------------------------------------- |
| 01_Abstractions    | `I+功能名称.cs`，前缀 I 表示接口               | `ICamera.cs`、`IPlc.cs`、`IAlgorithmService.cs`              |
| 02_Implementations | `品牌+功能名称.cs`，帕斯卡命名法               | `IkCamera.cs`、`SiemensPlc.cs`、`NLogLogger.cs`              |
| 03_Services        | `功能名称+Service.cs`，后缀 Service 表示服务类 | `CameraService.cs`、`PlcService.cs`、`ConfigService.cs`      |
| 04_Business        | `功能名称+Process/Manager/StateMachine.cs`     | `DetectionProcess.cs`、`ProductionManager.cs`、`DeviceStateMachine.cs` |
| 05_ViewModels      | `功能名称+ViewModel.cs`，后缀 ViewModel        | `MainViewModel.cs`、`MonitorViewModel.cs`、`IoMonitorViewModel.cs` |
| 06_Views           | `功能名称+View.xaml`，后缀 View 表示界面       | `MonitorView.xaml`、`ParameterView.xaml`、`IoMonitorView.xaml` |
| 07_Models          | `实体名称.cs`，帕斯卡命名法                    | `Defect.cs`、`ProductRecord.cs`、`AppConfig.cs`              |
| 08_Data            | `功能名称+Context/Manager/Repository.cs`       | `DatabaseContext.cs`、`FileManager.cs`、`DefectRepository.cs` |
| 09_Common          | `功能名称+Converter/Extension/Helper.cs`       | `BoolToColorConverter.cs`、`BitmapExtensions.cs`、`ImageHelper.cs` |

### 三、类和方法命名规范

| 类型 | 规范                          | 示例                                                      |
| :--- | :---------------------------- | :-------------------------------------------------------- |
| 类   | 帕斯卡命名法，名词或名词短语  | `CameraService`、`DetectionProcess`、`Defect`             |
| 接口 | 前缀 I + 帕斯卡命名法         | `ICamera`、`IPlc`、`IDataService`                         |
| 方法 | 帕斯卡命名法，动词或动词短语  | `GetBitmap()`、`WaitForStartTrigger()`、`DetectDefects()` |
| 属性 | 帕斯卡命名法，名词或名词短语  | `ExposureTime`、`IsRunning`、`TotalCount`                 |
| 事件 | 帕斯卡命名法，动词 + 时态后缀 | `DefectDetected`、`ProcessCompleted`、`StatusChanged`     |

### 四、工业场景特殊命名规范

1. **硬件相关命名**：必须带品牌前缀，避免混淆

   

   - ✅ `IkCamera`、`SiemensPlc`
   - ❌ `Camera`、`Plc`（不知道是哪个品牌的）

   

2. **PLC 地址相关命名**：不要用魔法数字，用有意义的常量

   

   csharp:

   ```c#
   // ✅ 正确
   public const string StartTriggerAddress = "M100";
   public const string EndTriggerAddress = "D200";
   
   // ❌ 错误
   _plc.WriteShort("D200", 3);
   ```

   

3. **状态和事件命名**：使用过去分词表示已发生的事件

   

   - ✅ `DefectDetectedEvent`（缺陷已检测到）
   - ✅ `ProcessCompletedEvent`（流程已完成）
   - ❌ `DetectDefectEvent`、`CompleteProcessEvent`

## 工业项目最佳实践总结

1. **严格执行文件位置检查**：在代码审查时，首先检查文件是否放在了正确的文件夹中。这是最容易执行也是最有效的规范。
2. **新人培训第一节课讲项目结构**：让每个新人在写第一行代码之前，就清楚每个文件夹应该放什么文件。
3. **定期清理无效文件**：删除不再使用的文件，保持项目结构整洁。
4. **不要随意新增根文件夹**：如果需要新增根文件夹，必须经过团队讨论，确保符合分层架构原则。
5. **所有配置都要放在 Configs 文件夹**：绝对不要在代码中硬编码任何参数。
