# 999999009-29_NLog 异步写入完整底层原理

## 一、核心模型：生产者 - 消费者队列（核心本质）

NLog 异步的底层是标准**生产者 / 消费者（Producer-Consumer）** 模型，分为两层角色：

1. **生产者**：你的业务线程（相机回调、PLC 控制、UI 主线程、算法线程）
2. **消费者**：NLog 内部单独创建的**后台低优先级专用写盘线程**
3. **缓冲媒介**：线程安全内存队列（`ConcurrentQueue` 实现）

### 整体一句话逻辑

业务线程只做一件事：把日志消息丢进内存队列，立刻返回，**不碰任何磁盘 IO**；

后台专属线程循环从队列捞取日志，批量写入文件 / 数据库，磁盘耗时完全隔离到后台线程，不会阻塞产线实时逻辑。

## 二、两种异步开启方式底层统一：AsyncWrapper

无论你写全局 `<targets async="true">`，还是单独给文件套 `<AsyncWrapper>`，底层逻辑完全一致：

`<targets async="true">` 只是语法糖，会自动给内部每一个 Target 外层包裹 `AsyncWrapper` 包装器类。

`AsyncWrapper` 是实现异步的核心组件，内部封装：

1. 线程安全阻塞队列（带容量上限 queueLimit）
2. 独立后台消费线程
3. 批量写入缓存缓冲区（batchSize）
4. 队列溢出策略处理器（Discard / Block / Grow）

## 三、分步完整执行流程（一次日志调用全链路）

以 `LogHelper.Info("线扫相机", "相机启动成功")` 为例，分 6 步拆解：

### 步骤 1：业务线程组装日志事件 LogEventInfo

业务代码传入模块、消息、异常，NLog 内部封装成轻量对象 `LogEventInfo`，包含：时间戳、日志级别、线程 ID、自定义属性（Module/BatchNo）、异常对象。

> 注意：字符串格式化、ScopeContext 属性注入**在生产者线程（业务线程）执行**，这也是高频循环不要写复杂格式化的原因，会增加业务线程耗时。

### 步骤 2：AsyncWrapper 接收 LogEventInfo，尝试入队

AsyncWrapper 拿到日志对象，判断当前队列长度是否达到 `queueLimit` 上限：

1. 队列未满：直接入队，业务线程**微秒级直接返回**，无阻塞；
2. 队列已满：执行配置的 `overflowAction` 策略：
   - `Discard`（工业推荐）：直接丢弃这条新日志，业务线程立刻返回，绝不卡住产线；
   - `Block`：业务线程阻塞等待队列腾出空位（工控严禁使用，会卡死相机 / PLC 线程）；
   - `Grow`：无限扩容队列，极端异常场景内存持续暴涨，程序 OOM 崩溃。

### 步骤 3：业务线程执行完毕，继续跑原有逻辑

入队操作完成，相机采集、PLC 周期控制不受任何 IO 影响，CT 几乎无增加。

**磁盘写入延迟、文件卡顿、硬盘读写波动全部隔离，和业务线程完全解耦。**

### 步骤 4：后台消费线程持续阻塞等待队列数据

NLog 在程序启动时，为每个独立 AsyncWrapper 启动一条**后台、低优先级**线程：

csharp:

```c#
new Thread(ConsumerLoop)
{
    IsBackground = true,
    Priority = ThreadPriority.BelowNormal // 低于采集、控制线程，不抢占实时算力
}.Start();
```

该线程循环阻塞读取队列，无日志时休眠，不占用 CPU。

### 步骤 5：批量聚合日志，减少磁盘 IO（batchSize 机制）

消费线程不会来一条写一条，而是：

1. 从队列一次性取出最多 `batchSize` 条日志；
2. 合并为一批，一次性调用底层 File Target 写入磁盘；
3. 写完后休眠 `timeToSleepBetweenBatches` 毫秒，再取下一批。

**关键优化价值**：机械硬盘单次打开 / 写入 / 关闭开销极高，批量写入能把上千次小 IO 合并为 1 次大 IO，磁盘压力降低 90% 以上。

### 步骤 6：底层 Target 统一落地（同步写文件）

批量拿到日志后，消费线程内部调用原始 File Target 同步执行文件写入、追加、换行。

这里的 “同步写盘” 仅发生在后台专属线程，**不会影响任何业务代码**。

## 四、关键配套机制底层原理

### 1. keepFileOpen 长期持有文件句柄

File Target 开启 `keepFileOpen="true"` 后：

- 第一次写入时打开文件流，缓存文件句柄；

- 批量写完不关闭流，下次直接复用；

- 只有跨天切割、程序退出、长时间无日志（openFileCacheTimeout）才释放句柄。

  避免每次批量写入都重复 `Open→Write→Close`，大幅降低 IO 系统调用开销，适配 100fps 高速采集场景。

### 2. 程序 Shutdown 强制刷盘机制

异步日志存在内存队列，程序强制关闭时队列中未写入磁盘的日志会丢失，因此 `LogManager.Shutdown()` 底层逻辑：

1. 标记所有 AsyncWrapper 停止接收新日志；

2. 阻塞等待后台消费线程把队列内剩余全部日志批量写入磁盘；

3. 关闭所有文件流、释放句柄；

4. 销毁后台消费线程。

   

   全局崩溃、窗口关闭时调用，保证故障堆栈日志不丢失。

### 3. 多 Target 独立队列隔离（工业核心优势）

如果给相机、PLC 分别配置独立 AsyncWrapper，会创建两套完全隔离的队列 + 消费线程：

- 相机高刷屏海量日志只会填满相机专属队列，溢出丢弃相机日志；

- PLC 控制日志队列不受挤压，关键报警、错误日志正常留存；

  

  全局同步 Log4Net 无法实现队列隔离，海量视觉日志会阻塞控制日志写入，这是 NLog 工控场景核心优势。

### 4. ScopeContext 上下文传递原理

`ScopeContext.PushProperty("Module", "线扫相机")` 底层基于**异步本地存储 AsyncLocal**：

- 同一调用链（采集回调、子函数）自动携带自定义属性；
- 多线程、异步任务不会串上下文，打印日志自动拼接模块、批次、操作员，不需要每条日志手动传参。

## 五、异步与同步写入底层核心差异对比

| 环节         | 同步写入（无 AsyncWrapper）     | NLog 异步写入                     |
| :----------- | :------------------------------ | :-------------------------------- |
| IO 执行线程  | 当前业务线程（相机 / PLC）      | 独立后台低优先级线程              |
| 单条日志耗时 | 3~20ms（磁盘波动影响极大）      | 0.1ms 以内，仅入队操作            |
| 磁盘卡顿影响 | 直接拉高 CT、丢帧、控制周期抖动 | 完全不影响业务，仅后台延迟写盘    |
| IO 频次      | 一条一写，频繁打开关闭文件      | 批量聚合写盘，IO 次数大幅减少     |
| 队列限流     | 无，海量日志瞬间打满磁盘        | queueLimit 限制内存上限，防止 OOM |
| 溢出处理     | 无，线程卡死等待磁盘            | 可配置丢弃新日志，优先保障生产    |

## 六、工业场景关键底层结论（贴合你的上位机开发）

1. **异步不会消除磁盘写入耗时，只是转移耗时线程**

   

   磁盘写入的耗时客观存在，但被转移到不影响生产的后台线程，实时采集 / 控制逻辑零干扰；

2. 业务线程仍有微小开销：日志对象封装、字符串格式化、入队内存拷贝，因此高频帧循环只允许 Debug 日志，生产关闭；

3. `overflowAction="Block"` 绝对禁用：一旦队列塞满，相机回调线程会阻塞等待写盘，直接变回同步日志，丢帧、漏检；

4. 多模块分离异步队列是高可靠产线标配，避免大量视觉日志淹没 PLC 故障日志；

5. 后台线程优先级低于业务线程，系统算力紧张时优先保障图像采集、运动控制，日志写入让步。
